# PDCA ワークフロー

**トリガー:** `/pdca`（またはユーザーが「レビュー→計画→改修→コミットを回したい」と求めた場合）

**説明:**
`レビュー → 計画 → 改修 → コミット` の改善サイクルを、メインセッション（設計・監査担当）が
オーケストレーションし、実装は **モデル別サブエージェントへ委譲** してトークンを節約しながら回す。

このワークフローは `.agents/rules/agent-orchestration.md`（役割分担）、`.agents/rules/plan-before-modify.md`
（事前計画・承認）、`.agents/rules/git-commit-rules.md`（コミット規約）に従う。引数 `$ARGUMENTS` が
あれば、今回のサイクルで扱う対象・観点として解釈する。

---

## フェーズ1: レビュー (Check) — 読み取り専用

- **目的:** 現状を監査し、改善対象を特定する。
- **アクション（メインが実施）:**
  - `git status` / `git diff` で直近の変更を把握する。
  - `CHANGELOG.md` と `docs/history/`・`docs/issues/` の関連ドキュメントで意図を確認する。
  - `/review` のレンズ（バグ・セキュリティ・パフォーマンス・可読性／論理）で問題を洗い出す。
  - **このフェーズでは変更を加えない。**
- **出力:** 🔴重大 / 🟡提案 / 🟢称賛 に整理した所見。

## フェーズ2: 計画 (Plan) — 承認ゲート

- **目的:** 改修方針を確定し、ユーザー承認を得る。
- **アクション（メインが実施）:**
  - フェーズ1の所見から、今サイクルで対応する項目を選ぶ。
  - 修正計画を作成する: **目的 / 現状分析 / 提案変更（対象ファイル・具体ロジック）/ 検証計画 / リスク**。
  - **各改修項目に難易度ラベルを付け、委譲先を決める**（次表）:

    | 難易度 | 委譲先 |
    |---|---|
    | ルーチン・標準 | `implementer-sonnet`（Sonnet） |
    | 難所 | `implementer-opus`（Opus） |
    | 最難所 | メインが直接実装 |

  - 計画を `docs/history/YYYYMMDD-HHMMSS-theme-plan.md` に保存する。
- **停止条件（必須）:** 計画をユーザーに提示し、**明示的な承認（「進めてください」等）を得るまで改修に進まない。**
  方針説明を実装許可と見なさない（`plan-before-modify` 準拠）。

## フェーズ3: 改修 (Do) — サブエージェントへ委譲

- **目的:** 承認された計画を実装する。メインはコンテキストを設計・監査に温存する。
- **アクション:**
  - 各改修項目を、フェーズ2で決めた委譲先へ **Task ツールで委譲** する:
    - ルーチン → `implementer-sonnet`、難所 → `implementer-opus`、最難所 → メイン直接。
  - 委譲時は **完結した仕様（対象ファイル・変更内容・検証方法）** を渡す。設計判断はサブエージェントにさせない。
  - 独立した複数項目は、可能なら **並行して** 委譲しトークン・時間を節約する。
  - サブエージェントの報告（変更点・検証結果・未対応）を受け取る。

## フェーズ4: コミット (Act) — 監査してから記録

- **目的:** 成果を監査し、規約どおりに記録・反映する。
- **アクション（メインが実施）:**
  - **監査ゲート:** サブエージェントの差分を `git diff` でレビューする。問題があればフェーズ3へ差し戻す。
  - 検証を実行する（該当テスト・lint 等）。失敗したら修正してから進む。
  - `.agents/rules/git-commit-rules.md` に従い Conventional Commits でコミットする
    （1コミット1変更。複数 type にまたがるなら分割）。
  - 結果を `docs/history/YYYYMMDD-HHMMSS-theme-result.md` に保存する
    （変更内容・検証結果・未対応事項を明記）。
  - `CHANGELOG.md` の「履歴一覧」末尾に、計画・結果doc へのリンク付きで1エントリ追記する。
  - 指定の作業ブランチへ push する（`.agents/skills/git-push/`）。
  - **プルリクの作成:** push 後、対象ブランチから **プルリクを作成する**。
    - タイトルは Conventional Commits 準拠（例: `feat(...): ...`）、本文には目的・変更概要・
      検証結果・関連 `docs/history/` リンクを日本語で記載する。
    - 既に同ブランチの PR が存在する場合は、新規作成せず本文を更新する。
    - レビュー対象を明確にするため、サイクルで対応した項目と未対応事項を箇条書きで含める。
  - **プルリクの購読（必須）:** 作成（または更新）した PR を `subscribe_pr_activity` で**必ず購読する**。
    - CI の失敗・レビューコメントを検知して対応するため、PR ごとに毎回購読する。
    - 購読後は現在の CI 状況と未対応レビューコメントを確認し、必要な対応を行う。
    - 購読は PR が **マージまたはクローズ** されるまで継続する。

---

## サイクルの継続

- 1サイクル完了後、未対応項目や新たな所見があれば **フェーズ1へ戻る**。
- 各フェーズの開始時に、現在どのフェーズにいるかを一言で明示する（透明性）。
- 速度より正確さとアーキテクチャ整合性を優先する。
