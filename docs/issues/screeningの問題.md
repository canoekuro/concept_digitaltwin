## 調査結果（2026-07-30）

独立した3つの欠陥が重なっていた。1が「いくらいじっても同じ結果になる」の主因。

### 1. 判定プロンプトに、設定から触れない一文が割り込んでいた

`build_judge_messages()` が組み立てる user メッセージは常にこの順だった。

```
■人物一覧 … / ■対象者条件 …
すべての条件を満たす人物を選んでください。   ← logic: "all" から生成。YAML から触れない
{screening.prompt.rule}                      ← ここだけ設定可能
```

`logic` が `all` である限りこの文が入り、しかも system prompt より近く `rule` の直前という
最も効く位置にある。パターン2は「条件に明確に反する人物だけを除外する」除外型に倒そうと
しているが、その直前で真逆の指示に引き戻されるため、パターン1と同じ挙動になっていた。

**対処:** この一文を廃止し、判定の指示は `screening.prompt.rule` に一本化した。
`logic` は `infer` では何もしなくなるので、書いたら調査定義の読み込みで停止する
（`ask` の `pass_if` の結合方法としては今も有効）。

### 2. 判定結果が再利用され、プロンプトを変えても聞き直していなかった

`screener_responses` は `(survey_id, persona_uuid, question_id)` で upsert されるだけで、
判定設定はキーに入らず、無効化する経路が無かった。同じ `survey_id` で回し直すと、
プロンプトやモデルを変えても古い判定がそのまま使われる。

**対処:** `screener_responses` に `config_hash`（判定設定の指紋）を持たせ、現在の設定と
一致する行だけを「判定済み」として扱うようにした。プロンプト・モデル・ペルソナカード・
条件を変えれば自動的に聞き直しになる。`oversample_factor` は判定の中身を変えないので
指紋に含めない（含めると再試行のたびに全件聞き直しになる）。設定を変えずに引き直したい
場合のために `persona-sim screen --force` を足した。

### 3. 到達不能でも倍率を上げ続けていた

通過率0.9%のとき、`oversample_factor` を 4→8→16→32 と倍にしても通過率は変わらないので
必要数（10名）には届かない。上限の32倍でも候補は320名までで、必要な候補は約1067名。
届かない再試行に4回分の判定呼び出し費用がかかっていた。

**対処:** 各試行の後に `実測通過率 × 上限倍率 >= 1` を確かめ、満たさないセルがあれば
上限まで試さずに E2 で停止する。停止メッセージに必要な候補数の見積もりを添える。

```
スクリーニング通過者が必要数に満たない（実インシデンスが低く、oversample_factor を
上限の 32 倍まで上げても必要数に届かないため、1 回で打ち切った）:
  M_20_29: 不足 7 名（通過 3 / 判定 320）
    必要な候補数の見積もり 約1067名（現在の通過率 0.9%）に対し、上限の 32 倍でも 320 名までしか増やせない
実インシデンス: M_20_29=0.9% / total=0.9%
```

### 残る論点（この修正のスコープ外）

**通過率0.9%そのものは、実装の不具合ではなく方式の限界の可能性が高い。**
判定カード（`screening.persona_card`）に載るのは属性行・総括文・`hobbies_and_interests` で、
「缶チューハイ・缶ハイボールを月1回以上飲む」を判断する材料は基本的に書かれていない。
書かれていないものを「蓋然性が高い」で厳格に選ばせれば、酒に言及したごく一部しか残らない。

上記1の修正でプロンプトが効くようになるので、まず除外型の `prompt.rule` で通過率が
妥当な水準に上がるかを確認すること。上がらない場合、飲用頻度のような条件は `infer` では
なく `ask`（本人に聞く／インシデンスを実測できる）か `assume`（前提として与える）が筋。
