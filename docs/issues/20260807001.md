# 出力長超過（`max_tokens` 到達）でセッションが丸ごと失われる

3600セッションの本番実行で4セッション（0.11%）が失敗した。

## 観測されたもの

```
失敗      : 4
警告 LLMError: databricks:databricks-gpt-5-6-luna の呼び出しに失敗: {
  "error": {
    "message": "Could not finish the message because max_tokens or model output limit was reached. Please try again with higher max_tokens.",
    "type": "invalid_request_error",
    "param": null,
    "code": null
  }
}
```

同じ警告が3件。**失敗4件に対して警告が3件なのは矛盾ではない。**
`persona_sim/run/run.py` の `_summarize` が `execution.errors[:3]` しか警告に載せないため。
4件目も同じエラーである可能性が高いが、この出力からは確認できない。

## 何が起きていたか

エンドポイントが HTTP 400 を返し、`persona_sim/llm/databricks.py` の `_is_retryable()`
（429 と 5xx のみ真）が偽なので、非リトライ分岐から即座に `LLMError` として送出される。
これが `_ask` → `run_session` を素通りし、`persona_sim/run/executor.py` の `_collect` で
セッション失敗として計上される。

**失敗したセッションは1行も書き出さない。** `_collect` は `future.result()` が成功したときだけ
`records.extend` するので、そのペルソナが既に答え終えていた設問の回答まで丸ごと失われる。
欠けたのは4回答ではなく4セッション分の全設問。

## これは設定不足ではない

3596セッションが同じ `max_tokens` で通っている。決定論的な設定ミスなら全滅するはずで、
0.11% だけが落ちるのは**出力長が非決定的に揺れ、稀に予算を超える**という分布の裾の事象。

したがって分類が事実と合っていない。400 は本来「何度投げても同じ」を意味するが、この 400 は
リクエストの不正ではなく、同じ入力の再送——それも枠を広げた再送——に意味がある。

`_ask` は既にパース失敗に対して同じ理屈で再送している（`persona_sim/run/session.py`）。

> 再送は同じ入力で行う。サンプリングパラメータは指定していないので、揺れを作るのは
> エンドポイント側の非決定性だけ。

同じ非決定性が原因である出力長超過だけが1回で諦めていた。

## 実行自体は正しく完走している

E5 の閾値（`executor.py` の `CONSECUTIVE_FAILURE_LIMIT = 20` / 直近100セッションで失敗率50%）
にも、品質フラグの警告閾値5%にも遠く及ばない。中断せず最後まで走ったのは設計どおりで、
この調査結果自体は使える。

## 併せて見つかった穴

**`finish_reason` をどこでも見ていなかった。** `_to_completion` は
`choices[0].message.content` と `usage` しか読まない。今回のエンドポイントは 400 を返したが、
200 + `finish_reason: "length"` で途中までの本文を返す挙動なら、**切り詰められた回答が
フラグなしで `answer_raw` / `answer_text` に流れる**。`_content_to_text` の docstring が
守っている「黙って劣化した経路に落ちない」が、この経路だけ抜けていた。

## 裾が存在する理由（本issueの対象外）

`docs/issues/202607281100.md` の既知未修正issue——`model.thinking` が validate と
`run_metadata.json` にしか存在せず**リクエスト payload に一切載っていない**——が原因と見られる。
エンドポイントは既定どおり思考し、推論トークンが出力予算を食う。

**予算超過の発生頻度そのものは、あちらを直すまで下がらない。**

## 対処

`docs/history/20260807-052000-output-limit-retry-plan.md` で対応済み。

- 出力長超過を `OutputLimitExceeded` として `LLMError` から分離
- 予算を段階的に引き上げて再送（`persona_sim/llm/budget.py`）
- 天井まで広げても通らなければ、セッションを殺さず `output_limit` フラグを立てて記録
- `finish_reason: "length"` も同じ経路に載せる
- 引き上げの実績を `run_metadata.json` と `[W_OUTPUT_LIMIT]` 警告に表面化

失敗した4セッションは、**同じコマンドの再実行**で埋まる。`run.py` の `_session_completed` により
未完了の4件だけが走り、3596件は `sessions_skipped` に落ちる。
