## 設計判断

### 1. LLM クライアントは差し替え可能にする

`LLMClient` プロトコルに対し、Databricks 実装と決定論的 Fake を用意する。
`model.endpoint` が `databricks` / `fake` / `azure_ai_foundry`（未実装）を取る。

`databricks-sdk` の `serving_endpoints.query` は `extra_params` が `Dict[str, str]` で
構造化出力の入れ子スキーマを渡せないため、OpenAI 互換の invocations エンドポイントを
`api_client.do` で直接叩く。認証は SDK の既定の認証チェーンに任せ、トークンもワークスペース URL も
コードとジョブ定義に書かない。

`azure_ai_foundry` はこの環境から疎通確認できないため、動かないアダプタを入れずに
「未実装」として `validate` と `registry` の両方で停止させる。

### 2. 実行単位は「セッション」。`memory` がその粒度を決める

| `design.memory` | 1セッションの範囲 |
|---|---|
| `none`（既定） | (ペルソナ, コンセプト, 設問) 1件 |
| `within_stimulus` | (ペルソナ, コンセプト) の全設問 |
| `full_session` | ペルソナの全コンセプト × 全設問 |

セッション内は逐次、セッション間は並列。投入順は §6.2 に従い、`memory: none` では
コンセプト外側・ペルソナ内側に並べて prefix cache を効かせる。

### 3. 再開の粒度もセッション

途中まで終わったセッションは丸ごとやり直す。途中だけ埋めると `full_session` で本来あった
会話履歴が無いまま後半の設問に答えることになり、再開前後で回答の意味が変わる。
M6 の完了条件「中断→再開で結果が一致する」はこの粒度でないと満たせない。

「完了」は、行が存在し、かつ閉じた設問で `parse_error` が立っていないこと。

### 4. 構造化出力は `auto` で、フォールバックを必ず記録する

`model.structured_output`（`auto` / `always` / `never`）を追加。`auto` は構造化出力を試し、
エンドポイントが受け付けなければ正規表現パースへ1回だけ切り替え、**その事実を実行メタデータに
記録して警告する**。黙って落とすと「構造化出力を使っているつもり」で精度が下がる。

### 5. `answer_code` は提示順の番号

`randomize_options` でシャッフルした場合、`options_order` に「定義順番号を提示順に並べたもの」を
記録し、`answer_code` は提示順の番号で保存する。定義順への読み替えは集計側（M5）で行う。
生データはモデルが実際に見たとおりに残す。

### 6. 再現性の範囲を仕様に明記する

`AGENTS.md` の「seed が揃えば同一結果」はパネル構築では成立するが、**LLM の生成結果は
エンドポイント側の非決定性により保証できない**（temperature 0 でも揺れ、リトライでは 0.3 に上げる）。
保証するのは入力側の再現性であると `SPEC_PHASE1.md` §9.1 と `AGENTS.md` に書き分ける。
書かないと満たせない約束が残る。
