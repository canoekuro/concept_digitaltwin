# コンセプト調査 Web UI アプリの実装（計画）

- 日付: 2026/07/28 23:30
- 対象: `docs/SPEC_UI.md` のうち、設定層より先（読み取り経路・投入・画面）

## 背景

仕様と設定層（`config/ui_config.yaml` ＋ `persona_sim/uiconfig/`）は先行して入っている。
アプリ本体を作るにあたり、ユーザーの決定は次のとおり。

1. 読み取り経路は **SQL Warehouse 経由**（Spark を使わない）
2. 画面2 は調査を選び「データを取得」ボタンで、結果テーブルに属性を join して取得する
3. **可視化のための加工は Databricks Apps 内で行う**
4. **実行進捗の表示は不要**。ジョブで非同期処理し、完了したら画面2 で選択可能になる
5. 調査定義は **Volumes に YAML を置いて**ジョブに渡す
6. ジョブは**事前定義したものを `run_now`** で起動する
7. 調査名に加えて**調査の種類**もテーブルに持つ

4 により、当初仕様にあった `runs` の実行状態列（`status` / `job_run_id` / `error_message`）と
進捗ハートビートは不要になる。完走後に1行 append される現在の挙動が、そのまま
「完了したら選択可能」と一致する。

## 実装可能性の確認

アプリ側のコードは pyspark 無しで動くことを import で確認した。`persona_sim/aggregate/`
配下はどのモジュールもモジュール先頭で pyspark を import していない（`TYPE_CHECKING` か
関数内のみ）。Spark が要るのは `frame.load_answers()` と `panel_composition_table()` の2箇所だけで、
ここに継ぎ目を入れれば集計の算術はすべて共有できる。

## 手順

1. **集計の継ぎ目**: `frame.answers_from_rows()` / `aggregate.build_result()` /
   `panel_composition_table_from_rows()` を切り出す。振る舞いは変えない
2. **調査の種類**: `SurveyType(StrEnum)` と `survey.type`（既定 `concept`）を追加
3. **`runs` の列**: `survey_name` / `survey_type` を追加（破壊的。既存テーブルは列追加が要る）
4. **SQL Warehouse 読み取り層**: `persona_sim/storage/warehouse.py`。
   クエリ組み立ては純関数、接続だけ薄い層。配列は `to_json` で文字列化して受け取る
5. **ジョブ投入層**: `persona_sim/uiconfig/jobs.py`。Volumes へ YAML、`run_now` で起動
6. **Streamlit アプリ**: `app/` に2ページ、`app.yaml`、`requirements.txt`
7. **仕様書・デプロイ手順・記録**: `docs/SPEC_UI.md` の §4/§6/§7、`deploy/README.md`

## 検証

Databricks 環境が無いので、検証できるものとできないものを分ける。

- 自動テスト: 既存が緑のまま（継ぎ目が振る舞いを変えていないこと）＋ 新規の純関数
- 実際に動かす: 画面1 をローカルで起動して操作する（Databricks に触らない範囲）
- 検証できない: SQL Warehouse への実接続、Volumes への書き込み、ジョブ投入、Apps へのデプロイ
