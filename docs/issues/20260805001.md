- UIから実行をしたところ、1度目の実行ではdocs/original.htmlのような結果でエラー、再実行となり、2度目の実行ではdocs/retry_1st.htmlのような形でエラー、再実行となった。これを修正したい。

## 調査結果（2026-08-05）

**2つのエラーは同じ1つの原因の症状**で、しかも表示されていた理由はどちらも事実と違う。
根は「`infer` 判定の LLM 呼び出しが全バッチ失敗したこと」だけ。

対象の実行は `survey_id=test_20260805021426_5803c0`、`mode: infer` /
`oversample_factor: 2` / `batch_size: 30`、候補は `M_20_29` の10名（要求5名×2）。

### 1度目（docs/original.html）: 中断が握りつぶされた

`screen_survey` は**例外を出さずに完了**し `確定: {} / 予備: {} / 非通過: {}` を表示、
次のセルの `run_survey` が `role=main のパネルが1件も無い。先に screen を実行すること`
で落ちた。

全バッチが `LLMError` で失敗すると `_infer_execution` が `aborted_reason` を立てるが、
その前に `screener_responses` へ行を書き、`return` して `finalize_panel` に到達しない
（パネルは `candidate` のまま）。`aborted_reason` は CLI は見ているのに、
`notebooks/run_survey.ipynb` の screen セルが見ていなかった。

### 2度目（docs/retry_1st.html）: 失敗が「非通過」として確定していた

`ScreenerShortfallError: 通過 0 / 判定 10、実インシデンス 0.0%、通過者が0名のため
候補を何倍に増やしても届かない` で停止。

1度目に書かれた10行が、現在の `config_hash` を持つ「判定済み・非通過」として読み戻され
（`read_screener_codes`）、`todo` が空 → **LLM を1回も呼ばないまま**全員 `screened_out`
に確定 → 通過率0と見て早期打ち切り。つまり**通信の失敗が「この人たちは条件に合わなかった」
という判定結果として永続化され、再実行しても二度と聞き直されない**状態だった。

`assume` のインシデンスを 1.0 と記録しない（聞いていないので測れていないのであって、
全員が該当したわけではない）のと同じ性質の誤りが、判定失敗側で起きていた。

### 対処

1. **判定できなかった候補を「判定済み・非通過」として残さない。**
   呼び出しが失敗した行にはスクリーナー専用フラグ `judge_error` を立て
   （`parse_error` = 返ってきたが番号が取れなかった、とは別物）、`read_screener_codes`
   がその行を返さないようにした。行自体は証跡として残す（`answer_raw` にエラー文）。
   再実行で聞き直され、同じ主キーなので upsert で上書きされる。
2. **中断をジョブの失敗にする。** ノートブックの screen セルが判定数を表示し、
   `aborted_reason` があれば例外を送出する（ノートブック冒頭の方針どおり）。
3. **中断理由に実際のエラー文を載せる。** 従来は「エンドポイントの設定を確認すること」
   だけで、原因は `screener_responses.answer_raw` を掘るまで読めなかった。

### 残る論点（この修正のスコープ外）

- **呼び出しがなぜ失敗したかは未確定。** エラー本文がどこにも出ていなかったため。
  修正版で再実行すれば screen セルがエラー文つきで止まるので、そこで
  判定エンドポイント側（存在・権限・レート制限）を切り分けること。
- **デプロイ済みアプリの設定が repo と食い違っている可能性。** 実行時の
  `ScreeningConfig` は `oversample_factor=2` / `persona_card` が既定の9項目だが、
  `app/config/ui_config.yaml` は `oversample_factor: 4` / 定性フィールド1項目。
  今回の失敗の原因ではないが、アプリの再デプロイが要るかもしれない。
- **一部のバッチだけが失敗した場合は、同じ誤りが小さい規模で残っている。**
  全バッチ失敗（今回の事例）は中断して確定させないが、一部だけ失敗してパネルが
  必要数を満たすと、`finalize_panel` が判定できなかった候補も `screened_out` にする
  （`passed` に居ない＝非通過、として扱うため）。実インシデンスがその分低く出る。
  正すには `finalize_panel` に「判定できた候補」を渡して未判定を `candidate` のまま
  残す必要があり、`_already_finalized` の意味づけにも及ぶので今回は見送った。
- **判定は成功したのに番号が1つも取れなかった場合**（「該当者なし」と出力不能の区別）は
  今も付いていない。今回の経路では起きていないが、別途検討する。
