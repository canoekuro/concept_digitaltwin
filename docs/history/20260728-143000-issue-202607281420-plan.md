# 計画: docs/issues/202607281420.md への対応

- **日時**: 2026/07/28 14:30
- **対象**: `persona_sim/` 全体 / `SPEC.md` / `README.md` / `AGENTS.md` / `notebooks/quickstart.ipynb`
- **完了条件**: 用語が `survey` に統一され、プロンプトが調査定義から編集でき、
  実際に送ったプロンプトが実行後に残り、第3のスクリーニング方式が選べる

## 1. 目的

`docs/issues/202607281420.md` に挙がった7件を解消する。内訳は用語の是正が1件、
スキーマの重複解消が1件、プロンプトの外出し・可視化が3件、Databricks 前提への追従が1件、
スクリーニング方式の新規追加が1件。

## 2. 現状分析

問題は3つに整理できる。

### 2.1 用語

「ジョブ／job」は社内で別の意味を持つ語で、調査基盤の中心概念の名前として誤読を招く。
`job_id` は全 Delta テーブルの主キー先頭列でもあり、放置すると後で直すほど高くつく。

### 2.2 プロンプトが固定

`[system]`・ペルソナカードの見出し・「番号のみで答えてください。」等の指示行が
`persona_sim/run/prompt.py` にハードコードされており、カテゴリごとに調整できない。
加えて実行後に「実際に何を聞いたのか」を確認する手段が無い。設定値だけでは
結局どう聞いたのかが読み取れない。

### 2.3 スクリーニングが二者択一

`ask` は費用と実行時間がかかり、`assume` は全候補に条件を強制するため矛盾したペルソナが
混じる。中間が無い。

### 2.4 その他

- `responses` / `screener_responses` に `answer_code` と `answer_codes` があり、
  前者は後者の射影で `multi` では常に null。列が2つあると集計経路が割れる。
- `image_uri` の説明が blob パス前提。フェーズ1の実行環境は Databricks。

## 3. 方針

`answer_code` 削除と `job_id` → `survey_id` はどちらも既存 Delta テーブルの作り直しを伴う。
**同一の破壊的変更としてまとめて実施する**（作り直しを2回に分けない）。

新方式 `infer` は既存の `ask` の経路（パネル確定・`screened_out` 保持・`cell_rank` 振り直し・
不足時の再試行）に乗せる。作り直すと不変条件を二重に実装することになる。

## 4. 変更内容

| 項目 | 内容 |
|---|---|
| 1 | `job` → `survey` を永続列まで含めて全面リネーム。旧 `job:` は書き換え方を添えて停止 |
| 2 | `answer_code` を廃し `answer_codes` に一本化。straightline 判定を `answer_codes[0]` へ |
| 3 | `PromptConfig` に `system` / `headings` / `rules` を追加。省略キーは既定のまま |
| 4 | 実行後に1ペルソナ分のプロンプトを `prompt_sample.md` と `run_metadata.json` に記録 |
| 5 | quickstart に `prompt` を追加し、`prompt_sample.md` の表示セルを足す |
| 6 | `image_uri` を Unity Catalog Volumes 前提にし、それ以外は警告 |
| 7 | `screener.mode: infer` を追加（`persona_sim/panel/infer.py` を新設） |

### 項目7 の設計

候補を `batch_size` 人ずつまとめて別セッションの LLM に渡し、条件合致の蓋然性が高い者を
選ばせる。判定ループは `run.executor` とは別に持つ（既存の `Session` は1ペルソナ1セッション
前提で、複数ペルソナを1回の呼び出しにまとめる `infer` とは形が合わない）。

- 判定モデルは `infer.model` で部分指定。書かなかったキーは調査本体の `model` を引き継ぐ。
  `thinking` は指定させず常に OFF（`AGENTS.md` 不変条件）
- 判定に見せる情報は `include_attributes` / `include_summary` / `persona_fields` で絞る。
  回答生成用のカードを流用すると1回のプロンプトが長くなり、費用面の利点が消える
- 通過率は**推定値**。`screener_incidence_estimated` に分けて記録し、実測値の欄には入れない。
  判定結果には `inferred` フラグを立てて実回答と区別する
- 判定条件（モデル・`batch_size`・見せた列）を実行メタデータに残す（§9.1 の再現性）
