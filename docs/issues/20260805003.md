## 確認結果（2026-08-05）

### 1. 回答生成側は数えていたが、スクリーナー側は数えていなかった

| | 実装状況 |
|---|---|
| 回答生成 | `RunResult.input_tokens` / `output_tokens` が既にあり、CLI（`persona-sim run`）は表示していた |
| スクリーナー | `ScreeningResult` に**トークンのフィールドが無かった**。行単位では `screener_responses` に書かれているが、結果オブジェクトが集計していなかった |

そのため今回、スクリーナー側の集計を新設したうえで表示セルを足した。

### 2. `infer` はレコードを合算してはいけない

`mode: infer` は**1バッチ＝1呼び出し**だが、`screener_responses` には候補1人につき1行を
書き、その行すべてに同じバッチのトークン数を載せている（`_to_record`）。回答生成側と同じ
「レコード単純合算」をそのまま持ち込むと、1回しか呼んでいないのに `batch_size` 倍
（設定値では30倍）に膨らんだ数字が出る。**呼び出し単位で足す**ようにし、テストで固定した。

副次的に分かったこととして、**`screener_responses` テーブルの `input_tokens` 列は
`infer` 行では人数ぶん重複している**。バッチを識別する列が無いためテーブルからの正確な
集計はできない。今回はテーブルを読まずメモリ上の呼び出し結果から数える設計にして回避した。
保存形式は変えていない（列を足すと既存テーブルの移行が要る）。

### 3. 集計範囲は「この実行ぶん」

再開でスキップしたセッションと、判定済みで聞き直さなかった候補は含まない。
`run_metadata.json` の `tokens_scope: "run"` と同じ範囲で、**今回の実行でいくら使ったか**を
答える数字になる。`assume` やスクリーナー無しの調査ではスクリーナー側が 0 になる。

調査全体の累計を出す案も検討したが、上記2の理由で `infer` のスクリーナー行を正しく
合算できないため採らなかった。

### 4. 表示

最終セルに、スクリーナー／回答生成／合計の3行を入力・出力の2列で出す。金額換算は載せない
（単価はワークスペースごとに違い、システム側に持たせると必ず古くなる。`SPEC.md` §9）。

```
区分                      入力          出力
--------------------------------------------

--------------------------------------------
合計                46,913,468     2,434,690
```
