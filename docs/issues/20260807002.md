# 高 — 結果の意味が変わる / 実行が壊れる

## H1. `__version__` と `pyproject.toml` の version が食い違う

```python
# persona_sim/__init__.py:7
__version__ = "0.1.0"
```

```toml
# pyproject.toml:8
version = "0.3.0"
```

### 実測

インストールした状態で確認した（`./scripts/run-tests.sh` が作る `.venv` 上）。

```
$ uv run python -c "import persona_sim, importlib.metadata as m; \
    print(persona_sim.__version__, m.version('persona-sim'))"
0.1.0 0.3.0

$ uv run persona-sim --version
persona-sim 0.1.0
```

### なぜ問題か

`persona_sim/__init__.py` の docstring は「現在の実装範囲は M1 と M2」と書いているが、
実際には M1〜M7 と Web UI まで実装されている。版だけでなく説明も 0.1.0 の時点で止まっている。

影響が出るのは記録側である。

- `persona-sim --version` が `persona-sim 0.1.0` を出す
- `metadata.build_metadata()` が `run_metadata.json` に `persona_sim_version: "0.1.0"` を書く

`SPEC_PHASE1.md` §9.1 は「seed と各バージョンが揃えば、モデルへの入力が完全に再現できること」を
求めており、`persona_sim_version` はその「各バージョン」の一つ。これが実装を指していないと、
**過去の `run_metadata.json` を見ても、どの版のコードで走ったのか判別できない**。
0.1.0 と記録された実行が3つあっても、それぞれ別のコードかもしれない。

### 修正方針

`__version__` を `importlib.metadata.version("persona-sim")` から引き、pyproject を SSoT にする。
未インストール（リポジトリ直接実行）のフォールバックが要る。

```python
from importlib.metadata import PackageNotFoundError, version

try:
    __version__ = version("persona-sim")
except PackageNotFoundError:  # リポジトリから直接読んだ場合
    __version__ = "0+unknown"
```

`0+unknown` を返す経路が残るのが気になるなら、逆向き（`__init__.py` を SSoT にして
pyproject に `dynamic = ["version"]` を書く）でもよい。どちらでも**片方を消す**ことが本質。
`tests/test_repo_layout.py` に一致を検査するテストを足して再発を止める。

あわせて `__init__.py` の docstring の「現在の実装範囲は M1 と M2」も直す。

### 対応（2026-08-07・対応済）

**当初 `importlib.metadata.version("persona-sim")` から引く形にしたが、CI で落ちた。**

```
FAILED tests/test_repo_layout.py::test_version_matches_pyproject
E   AssertionError: assert '0+unknown' == '0.3.0'
```

CI はパッケージを**インストールしない**（`requirements-ci.txt` を入れて
pytest の `pythonpath = ["."]` で解決する）ので `PackageNotFoundError` になり、
フォールバックの `0+unknown` が入っていた。手元では `uv run` がプロジェクトを
ビルド＆インストールするため通ってしまい、気づけなかった。

これは**テストだけの問題ではない**。同じ経路（未インストールで sys.path から使う）は
Databricks のノートブックでも起きうるので、そのまま出していたら
`run_metadata.json` の `persona_sim_version` が `0+unknown` になっていた。
記録が要るのはまさにその経路なので、リテラルの `0.1.0` より悪い。

そこで**向きを逆にした**。`persona_sim/__init__.py` の `__version__` を唯一の出どころにし、
`pyproject.toml` は `dynamic = ["version"]` ＋
`[tool.setuptools.dynamic] version = {attr = "persona_sim.__version__"}` で読む。
二重定義は消え、かつ未インストールでも版が読める。

テストも「一致するか」から**「出どころが1つに保たれているか」**に変えた
（`pyproject` に版を直書きしていない・`dynamic` で解決している・
未インストールでも数字で始まる版が読める）。

```
# 未インストール（CI と同じ経路）
$ python3 -c "import sys; sys.path.insert(0,'.'); import persona_sim; print(persona_sim.__version__)"
0.3.0

# インストール済み
$ uv run persona-sim --version
persona-sim 0.3.0
```

## H2. `simultaneous` × `memory: none` で2問目以降の提示順が定義順に戻る

```python
# persona_sim/run/session.py:378
def _fallback_stimuli(unit: Unit, ctx: SessionContext) -> tuple[Stimulus, ...]:
    """セッションの先頭ユニットが提示物を持たない場合の保険。..."""
    if unit.stimulus_id == NO_STIMULUS:
        return ()
    if unit.stimulus_id == ALL_STIMULI:
        return tuple(ctx.stimuli[stimulus_id] for stimulus_id in ctx.stimuli)   # ←ここ
    return (ctx.stimuli[unit.stimulus_id],)
```

### なぜ問題か

`ctx.stimuli` は `run_survey()` が `{stimulus.id: stimulus for stimulus in survey.stimuli}` として
作る dict、つまり**調査定義の記述順**である。ペルソナごとの `assigned_stimuli` の順序を見ていない。

同時提示ではこの分岐に必ず入る。そして `_unit_groups()`（`session.py:237`）は
グループ**先頭のユニットにしか** `stimuli_to_present` を持たせない。

```python
# persona_sim/run/session.py:240-249（simultaneous 分岐）
presented = tuple(stimuli_by_id[stimulus_id] for stimulus_id in assigned)  # ペルソナごとの順
return [[
    Unit(..., stimuli_to_present=presented if index == 0 else ())
    for index, question in enumerate(survey.questions)
]]
```

`memory: none` では `build_sessions()` が

```python
sessions = [Session(persona_uuid, (unit,)) for ... for unit in group]
```

と**ユニット1つずつを独立セッションに割る**ため、2問目以降のユニットは
`stimuli_to_present` が空のまま自分のセッションの先頭になり、必ず fallback を通る。

結果として、`presentation: simultaneous` / `memory: none` /
`rotation: random` **または** `balanced` の組み合わせで

- **設問1** … ペルソナごとにローテートされた提示順
- **設問2以降** … 全ペルソナ共通の定義順

になる。同じ人に同じ案を、設問によって違う並びで見せていることになる。

`AGENTS.md` は次を不変条件に挙げている。

> `seed` と各バージョンが揃えば、モデルへの入力が完全に再現できること。（中略）
> 誰に・どのコンセプトを・**何番目に**・どの選択肢順で・どのプロンプトで聞いたか

`responses.options_order` は選択肢の順序しか残さないので、**コンセプトの提示順がずれたことは
どのテーブルにも残らない**。`run_metadata.json` の `prompt_sample` も1名の先頭設問だけなので、
ここには現れない。事後にログから気づく手段が無い。

### 影響範囲

現在の Web UI は `build_survey_dict()` が `presentation: sequential` を固定で書くので、
UI 経由では踏まない。**調査定義 YAML を直接書く CLI / ノートブック経路で
`simultaneous` を選んだ場合だけ**顕在化する。`design.rotation: none`（既定）なら
`assigned` も定義順なので実害は無く、`random` / `balanced` のときに限って結果が変わる
（`balanced` は `assignment_table()` が `cell_rank` ごとに巡回窓を作るため、
やはり定義順とずれる。`memory: none` では `W_ROTATION` 警告が出るが**停止はしない**）。

`sequential` 側（`return (ctx.stimuli[unit.stimulus_id],)`）は `stimulus_id` が
1件に定まるので正しい。問題は `ALL_STIMULI` 分岐だけ。

### 修正方針（2案）

**案A（推奨）: 提示順を全ユニットに持たせ、fallback の `ALL_STIMULI` 分岐を消す**

`_unit_groups()` で全ユニットに `stimuli_to_present` を入れ、履歴を持つモード
（`memory != none`）のときだけ2件目以降を空にする。`_fallback_stimuli()` の
`ALL_STIMULI` 分岐は削除する。

推測で埋める経路そのものが無くなるので、同じ穴が別の設計軸で再発しない。
`Unit` は `frozen=True` なので、グループを組む時点で `memory` を見る必要がある
（`_unit_groups()` に `survey.design.memory` を渡す）。

**案B: fallback に `assigned_stimuli` を渡す**

`SessionContext` にペルソナごとの `assigned_stimuli` を持たせ、
`_fallback_stimuli()` がそこから順序を復元する。差分は小さいが、
**提示順の出どころが `_unit_groups()` と `_fallback_stimuli()` の2箇所に残る**ので、
片方だけ直したときに同じずれが戻る。

いずれの案でも、回帰テストは
「`simultaneous` × `memory:none` × `rotation:random` で、同一ペルソナの全設問の
`stimuli_to_present` が一致する」を `tests/test_session.py` に足す。
このテストは現行コードで落ちることを確認してからコミットすること。

### 対応（2026-08-07・対応済）

**案A** で実施した。

- `_unit_groups()` に `keeps_history = survey.design.memory is not Memory.NONE` を持たせ、
  `stimuli_to_present` を `index == 0 or not keeps_history` で入れる。
  同時提示・逐次提示の両方の分岐に同じ条件を適用した
- `_fallback_stimuli()` の `ALL_STIMULI` 分岐を**削除**した。
  到達した場合は `KeyError: '*'` になる（推測で埋めるより落ちるほうがよい、という判断）。
  なぜ補わないかは関数の docstring に残した

テストは `tests/test_session.py` に3件追加。

- `test_simultaneous_without_memory_keeps_the_assigned_order_on_every_question`
- `test_sequential_without_memory_presents_on_every_question`
- `test_memory_keeps_presenting_only_at_the_group_head`（履歴ありは従来どおりの回帰）

前2件が修正前のコードで落ちることを確認済み。
Spark を使わずに `assigned_stimuli` の順序と突き合わせるため、
定義順と違う並び（`["c3", "c1", "c2"]`）を持つパネル行を直接渡している。

## H3. `infer` 判定の想定外例外で、完了済みバッチの結果ごと失われる

```python
# persona_sim/panel/infer.py:306-316
with ThreadPoolExecutor(max_workers=concurrency) as pool:
    futures = [pool.submit(judge_batch, group, personas, screening, client, model)
               for group in groups]
    for future in futures:
        batch = future.result()          # ← 裸
```

### なぜ問題か

`judge_batch()` が吸収するのは `except LLMError` だけである。それ以外の例外——

- `judge_batch:195` `ordered = [personas[uuid] for uuid in persona_uuids]` の `KeyError`
  （パネルにいて `personas_base` から消えたペルソナ。`load_personas()` が防いでいるが、
  ここは防御が二重になっていない）
- `parse_judgement()` / `build_judge_messages()` の想定外

——は `future.result()` から素通りして `run_inference()` を抜け、
`_infer_execution()` → `screen_survey()` と伝播してコマンドごと落ちる。

`screen_survey()` は `execution.records` を**受け取ってから** `merge_upsert` するので、
例外で抜けると**成功した他バッチの判定結果も1件も書き出されない**。
`infer` は1バッチ＝1呼び出しで、`batch_size: 20` なら数十〜数百バッチ動く。
最後のバッチで踏めば、それまでの全呼び出しが課金だけされて捨てられる。

`run/executor.py` の同じ立場のコードは、この危険を認識して吸収している。

```python
# persona_sim/run/executor.py:131-138
try:
    result.records.extend(future.result())
    ...
except Exception as exc:  # セッション単位で失敗を吸収し、調査全体は止めない
```

`infer` 経路だけが揃っていない。`judge_batch()` の docstring は
「失敗しても例外にせず、結果に理由を残して返す」「1バッチの失敗で調査全体を止めない」と
書いているので、**意図と実装が食い違っている**（意図のほうが正しい）。

### 修正方針

`run_inference()` のループで `future.result()` を包み、`InferBatchResult(error=...)` に落とす。
`judge_batch()` 側に `except Exception` を足すのでもよいが、
ワーカー内で捕り逃した場合の受け皿として呼び出し側にも置くのが確実。

`_collect()` は `batch.failed` のとき `result.codes` に入れず `judge_error` フラグ付きの
行だけを残すので、**再実行で聞き直される**（既にある良い劣化の仕方に乗る）。

テストは「1バッチが `LLMError` 以外の例外で落ちても、他バッチの `records` が残り
`batches_failed` に計上される」を `tests/test_infer.py` に追加する。

### 対応（2026-08-07・対応済）

`run_inference()` の受け取りを `_result_or_failure(group, future)` に切り出し、
`except Exception` で `InferBatchResult(error=...)` に落とすようにした。
`group` が要るので `zip(groups, futures, strict=True)` で回す。

`error` が入るので `failed` が真になり、既存の経路がそのまま働く
（`batches_failed` に計上 → `_collect()` が `codes` に入れず `judge_error` を立てる →
`read_screener_codes()` が未判定として除く → 再実行で聞き直される）。

テストは `tests/test_infer.py` に2件追加。どちらも修正前のコードで落ちることを確認済み。

- `test_run_inference_survives_an_unexpected_exception_in_one_batch`
  … クライアントが `RuntimeError` を投げるケース
- `test_run_inference_survives_a_persona_missing_from_the_mapping`

## H4. SQL Warehouse 接続を全 Streamlit セッションで共有している

```python
# app/lib/context.py:102
@st.cache_resource
def connection():
    """SQL Warehouse への接続。セッションをまたいで使い回す。"""
    from persona_sim.storage.warehouse import connect
    return connect(warehouse_id())
```

### なぜ問題か

`@st.cache_resource` はプロセス全体で1つのオブジェクトを共有する
（`@st.cache_data` と違い、利用者ごとには分かれない）。docstring の
「セッションをまたいで使い回す」はそのとおりだが、**またぐ相手は同一利用者の再実行だけではなく、
別の利用者の同時アクセスも含む**。

Streamlit は接続中のブラウザセッションごとに別スレッドでスクリプトを再実行する。
`databricks-sql-connector` の `Connection` / `Cursor` は
PEP 249 の threadsafety=1（モジュールは共有可、接続は共有不可）相当で、
複数スレッドから同時に `cursor.execute()` を呼ぶ前提で作られていない。

`warehouse.fetch()` は毎回 `with connection.cursor()` で新しいカーソルを開くが、
下層の Thrift セッションは1本なので、2人が同時に「データを取得」を押すと
リクエストが混ざる。壊れ方は運次第で、例外になるか、**片方の結果がもう片方に返る**。
後者は「別の調査の集計表を自分の調査だと思って読む」という、
`app/views/results.py` が `st.caption(f"survey_id: ...")` を出してまで防ごうとしている事故そのもの。

社内利用で同時アクセスが稀なら踏む頻度は低いが、踏んだときに気づけない種類の壊れ方である。

### 修正方針

接続キャッシュは残したまま、利用を直列化する。`app/lib/context.py` に閉じる。

```python
_QUERY_LOCK = threading.Lock()

def with_connection():
    """SQL Warehouse への呼び出しを直列化する。

    databricks-sql-connector の Connection は複数スレッドから同時に使えない。
    Streamlit は利用者ごとに別スレッドでスクリプトを再実行するので、
    ここで直列化しないとリクエストが混ざる。
    """
    ...
```

`app/views/results.py` の `warehouse.fetch_*` 呼び出しをこれで包む。
`persona_sim/storage/warehouse.py` 側は触らない（CLI・ノートブックは単一スレッドで、
ロックを持ち込む理由が無い）。

取得は「データを取得」押下時の1回だけなので、直列化しても体感は変わらない。

### 対応（2026-08-07・対応済）

`app/lib/context.py` に `_QUERY_LOCK` と `query(fetcher, *args, **kwargs)` を足し、
接続を渡す取得関数をすべてこれ経由にした。

- `app/views/results.py` の3箇所（`fetch_survey` / `build_result` / `fetch_responses_raw`）
- `context.runs()`（`fetch_runs`）

あわせて `runs()` の `_connection` 引数を落とした（`query()` が `connection()` から取るので
受け取る必要が無く、残すと「渡しているのに使っていない」引数になる）。
`results.py` の `connection = context.connection()` も不要になったので削除。
`persona_sim/storage/warehouse.py` は変更していない。

テストは `tests/test_results_page.py` に2件追加した。
この環境には streamlit が入っておらず `app/` を import できないので、
**ソースの形で固定する**方式にした。

- `test_the_page_never_passes_the_shared_connection_to_a_fetcher`
  … `context.query(` があり、`warehouse.fetch_*(connection` が無いこと
- `test_the_query_helper_holds_a_lock` … `with _QUERY_LOCK:` があること

**同時アクセスの実挙動は検証していない。** Streamlit のランタイムを模さないと
意味のある並行テストにならないため、実機確認は未実施のまま残る。

## M2. `_looks_like_output_limit()` が設定不正まで拾い、無駄に予算を広げる

```python
# persona_sim/llm/databricks.py:44
_OUTPUT_LIMIT_HINTS = ("max_tokens", "output limit", "max output")
```

```python
# persona_sim/llm/databricks.py:224-235
def _looks_like_output_limit(exc: Exception) -> bool:
    if _is_retryable(exc):
        return False
    status = getattr(exc, "status_code", None)
    if isinstance(status, int) and not 400 <= status < 500:
        return False
    message = str(exc).lower()
    return any(hint in message for hint in _OUTPUT_LIMIT_HINTS)
```

### なぜ問題か

判定は「400系」かつ「文言に `max_tokens` を含む」だけ。
`max_tokens` に触れる 400 は出力長超過だけではない。

```
"max_tokens must be less than or equal to 4096"
"Invalid value for max_tokens: expected integer"
```

これらは**リクエストの不正**——何度投げても同じ——だが、`OutputLimitExceeded` に分類される。
すると `budget.complete_within_budget()` が

```python
OUTPUT_LIMIT_MULTIPLIERS = (4, 16)
```

に従って**さらに大きい** `max_tokens` で2回投げ直す。上限超過が原因なら、
広げるほど確実に失敗する。1呼び出しが3倍に膨らみ、全セッションで起きるので
実行時間もエンドポイントの負荷も3倍になる。

そのうえ最終的な見え方が誤診に寄る。

- `responses` に `output_limit` フラグが立つ（＝「回答が切り詰められた」の意味）
- `[W_OUTPUT_LIMIT]` 警告が「天井（4,096）まで広げても完了せず」と出る
- 対処として「`model.max_tokens` を見直すこと」と案内される

**実際に必要なのは `max_tokens` を下げることなのに、上げるよう案内される。**

`docs/issues/20260807001.md` で対処したときに `finish_reason: "length"` を見る経路
（`_to_completion:331`）が入っており、そちらは根拠が明確で誤検知しない。
文言マッチはあくまで 400 を返すエンドポイント向けの補助である。

### 修正方針

補助側の判定を、打ち切りを示す語に絞る。

- 除外語を持つ: `must be` / `invalid` / `expected` を含むものは対象外
- または肯定条件を強める: `reached` / `was reached` / `truncat` / `finish` を要求する

`docs/issues/20260807001.md` に実際のエラー文言が記録されている。

> `Could not finish the message because max_tokens or model output limit was reached.`

`reached` を要求するだけで、この実例は拾い、`must be <= N` は落とせる。

テストは `tests/test_databricks_client.py` に
「`max_tokens must be <= 4096` は `OutputLimitExceeded` ではなく `LLMError`」を追加。

### 対応（2026-08-07・対応済）

`_OUTPUT_LIMIT_HINTS` を打ち切りを示す語だけに絞り
（`reached` / `output limit` / `max output` / `truncat`）、
`_INVALID_VALUE_HINTS`（`must be` / `invalid` / `expected` / `out of range` / `not allowed`）に
一致するものは除外するようにした。主経路が `finish_reason == "length"` である旨も
`_looks_like_output_limit()` の docstring に明記した。

テストは `tests/test_databricks_client.py` に4件追加。
値の不正3パターンが `LLMError`（かつ再試行せず1回で返す）ことと、
`docs/issues/20260807001.md` の実文面が従来どおり `OutputLimitExceeded` になること。

## M3. 推論リクエストの再試行が二重になっている（**当初の記述は誤り**）

> **訂正（2026-08-07）**
>
> この所見は当初「推論リクエストに**タイムアウトが無い**」「ハングした1件がワーカースレッドを
> **無期限に**占有する」「`concurrency: 32` が全部詰まると実行は**無言で停止**する」と
> 書いていた。**これは誤りだった。** 修正に着手して SDK の実装を読んだところ、
> `databricks-sdk` は既定でタイムアウトを掛けている。
> 実際に見つかった問題（再試行の多重化）に書き直した。

### 事実関係

`databricks-sdk` の `_BaseClient.__init__` は次の既定を持つ。

```python
self._retry_timeout_seconds = retry_timeout_seconds or 300
self._http_timeout_seconds = http_timeout_seconds or 60
```

- 1リクエストあたり **60秒**（socket レベルのタイムアウト）
- SDK 内部の `@retried` が **300秒**を上限に自前で再試行

つまり**無期限に詰まることは無い**。最終的に例外が返り、E5 の勘定に乗る。
なお `ApiClient.do()` には `timeout` 引数が無く、呼び出しごとには渡せない
（`Config` 経由でしか設定できない）ことも確認した。

### 残る本当の問題

**再試行の層が2つ重なっていて、片方が記録にも設計文書にも載っていない。**

```
persona_sim の _invoke_with_backoff … 5回まで、1→2→4→8秒と待って再試行
        ↑ この中で呼んでいる
databricks-sdk の内部再試行        … 300秒を使い切るまで再試行
```

外側が「1回失敗した」と数えるものは、**内側で既に何度か投げ直された後の結果**である。
両者は掛け算になるので、最悪で `5 × 300秒 ≒ 25分`を1回の `complete()` に費やしうる。

そのうえ2つ見えない。

- `RetryStats` が数えるのは外側だけなので、`run_metadata.json` の
  `model.endpoint_retries` からは SDK が何回眠ったかが読めない
  （`docs/history/20260806-071500-*` が可視化しようとした「429 で眠っていた」の一部が
  依然として見えない）
- `llm/budget.py` の冒頭は「この系には独立した再試行が**4つ**ある」と列挙しているが、
  SDK 内部の再試行は**5つ目の軸**として存在し、書かれていない。
  軸を混ぜるなと戒めている当のファイルが見落としている

### 対応（2026-08-07・対応済／挙動は変えていない）

**実行時の挙動は変えず、見えるようにした。**

1. `ModelConfig.request_timeout_sec`（既定 60 ＝ SDK の既定と同じ値）を追加し、
   `loader._model()` → `registry.build_client()` → `DatabricksServingClient` と渡して
   `WorkspaceClient(config=Config(http_timeout_seconds=...))` を組むようにした。
   **値そのものは変えていない**が、何秒で切れるのかが調査定義と
   `run_metadata.json` の `survey_definition` から読めるようになった
2. `llm/budget.py` の「再試行が4つ」を**5つ**に直し、SDK 内部の再試行を軸として書き足した。
   先頭2つが入れ子であることも明記した
3. `llm/databricks.py` のモジュール docstring に、SDK 内部にも再試行があること・
   `RetryStats` はこの層しか数えないこと・最悪で掛け算になることを書いた

**`retry_timeout_seconds` は触っていない。** 小さくすれば SDK 側の再試行は減るが、
こちらの `_RETRYABLE_ERROR_NAMES` は `ConnectionError` / `TimeoutError` を含まないため、
**今 SDK が吸収している接続リセットがそのまま致命傷になる**。
ほどくなら `_is_retryable()` の拡張とセットで行う必要があり、別サイクルに回した（未対応）。

### 対応（2026-08-08・完了）— **上の「掛け算」も誤りだった**

> **再訂正（2026-08-08）**
>
> 「両者は掛け算になる」「最悪 `5 × 300秒 ≒ 25分`」は**誤り**である。
> ほどく作業に入って `databricks-sdk` の `_base_client.py` / `retries.py` /
> `errors/customizer.py` を読み直したところ、**2つの層は重なっておらず、
> 失敗の種類で担当が分かれていた**。

| 失敗 | SDK 側 | 自前の層（`_invoke_with_backoff`） |
|---|---|---|
| 429 / 503 | `Retry-After` を尊重して再試行（300秒まで） | **到達しない** |
| 500 / 502 / 504 | 再試行しない | **ここが担当** |
| 接続リセット・socket タイムアウト | 再試行（300秒まで） | **到達しない** |
| 400 系 | 再試行しない | 分類して送出 |

429 / 503 に必ず `retry_after_secs` を付けるのは SDK 既定の `_RetryAfterCustomizer` で、
`retried()` はそれがあれば必ず投げ直す。だから**生の 429 は自前の層に出てこない**。
そして SDK が予算を使い切ると `TimeoutError("Timed out after 0:05:00") from 元の例外` を
投げるが、この名前は `_RETRYABLE_ERROR_NAMES` に無く `status_code` も持たないので、
`_is_retryable()` が偽を返して**その場で打ち切られていた**。掛け算になりようがない。

**残っていた実害はこちら。**

1. **SDK の枯渇が恒久エラーに化けていた。** 429 の嵐が300秒続くと
   `TimeoutError: Timed out after 0:05:00` という**レート制限だと読み取れない**文言の
   `LLMError`（＝再試行しても無駄）になる。最も再試行すべき状況の診断が最悪で、
   `concurrency: 32` なら32スレッドが各300秒を捨てて E5（連続20失敗）に至る
2. `_reason_key()` が `TimeoutError` を記録するので、429 だったことが
   `run_metadata.json` の `endpoint_retries.reasons` に残らない
3. 自前の層は 5xx 専用なのに5回・最大30秒のバックオフを持っており、
   担当範囲に対して過剰だった

**利用者の判断は「SDK に寄せて自前を薄く」＋「試行回数を減らす」。** 実施内容は次のとおり。

- `_unwrap_sdk_retry_timeout()` を新設し、SDK が包んだ `TimeoutError` を `__cause__` から
  **1段だけ**開いてから分類する。理由キーも例外の文面も元のステータスで残るようになった
- 開いた（＝ SDK が予算を使い切った）ものは**自前で投げ直さない**。既に300秒使った後で、
  二重に待つだけ通る見込みが無いため。ただし `LLMError` ではなく `RetryableLLMError`
  にして、記録に残るコードを実態に合わせた
- レート制限（429 / 503）だった場合は、文面に「`model.concurrency` を下げるか、
  エンドポイント側の割り当てを確認すること」を添える。
  **`W_ENDPOINT_RETRY` は 429 を数えられないので、ここが唯一の伝達経路になる**
- `max_attempts` を 5 → **3**。担当が 5xx だけなら3回で足り、早く失敗させたほうが
  E5 に早く届いて、詰まったまま課金され続ける時間が短い
- `_RETRYABLE_ERROR_NAMES` の 429 系は**残した**。SDK 経由では届かないが、
  `workspace_client` を注入する経路では来るし、将来 SDK が 429 を customizer から
  外したときに、消していると**無言で1回で捨てる**側に倒れる。安全側に残す旨をコメントにした

**`retry_timeout_seconds` は今回も触っていない。** SDK の `Retry-After` 尊重は
こちらの指数バックオフより正確で、下げても `retried()` は諦める前に必ず1回
`Retry-After` 秒眠る実装（`retries.py` の `clock.sleep()` は deadline の再確認より前）
なので得が無い。

**受け入れた穴**: 一本化を採らなかったので、**429・503・接続エラーの再試行は
`RetryStats` に載らないまま**。`llm/client.py` の `RetryStats` と `retry_warning()` の
docstring に「0 は詰まっていないの意味ではない」と明記し、黙った穴にはしていない。


## M4. E5 中断時に実行中セッションの結果を捨てている

```python
# persona_sim/run/executor.py:122-125
if result.aborted:
    for remaining in pending:
        remaining.cancel()
    pending = set()
```

### なぜ問題か

`Future.cancel()` は**まだ開始していない** future にしか効かない。
既に走っているものは False を返し、そのまま走り続ける。

`pending = set()` で while を抜けると `with ThreadPoolExecutor` の `__exit__` が
`shutdown(wait=True)` を呼び、走っていたセッションは最後まで完走する。
しかし `_collect()` を通らないので、**その結果は誰にも回収されず捨てられる**。

最大 `concurrency` 件（既定 32）のセッションぶんの LLM 呼び出しが、
課金されたうえで1行も残らない。再実行すれば `_session_completed()` が
未完了とみなしてもう一度呼ぶので、同じ費用を2回払う。

`execute()` の docstring はこう書いている。

> E5 を検知したら未着手のセッションを取り消し、**完了分を保存できる形で返す**。
> 例外にせず結果に載せるのは、途中まで書き出してから再開できるようにするため。

「未着手のセッションを取り消し」という書き方は正しいのだが、
**未着手でないものをどうするかが抜けている**。同じ関数の少し上には

```python
# 完了済みのぶんは中断が決まっていても取りこぼさない。
# ここで捨てると、書き出せたはずのセッションを再実行する羽目になる。
```

という、まさにこの問題を意識したコメントがある。`done` に入ったものは守られているが、
`pending` に残ったまま走り切るものが守られていない。

### 修正方針

`cancel()` が False を返した future は捨てずに待って回収する。

```python
if result.aborted:
    # cancel() はまだ始まっていないものにしか効かない。走っているぶんは
    # 待って回収する（捨てると、完走した呼び出しの費用だけ払って再実行になる）。
    still_running = {f for f in pending if not f.cancel()}
    for future in wait(still_running).done:
        _collect(future, result, detector)
    pending = set()
```

`_collect()` は `detector.record()` も呼ぶが、`result.aborted_reason` は
`if reason and not result.aborted` で最初の理由を保つので、中断理由は上書きされない。

「中断したのに待たされる」点は、中断後の待ちが最長1セッション分であること、
`raise_if_unrecoverable()` のメッセージで「完了した N セッション分は保存済み」と
出していることから、費用を捨てるより望ましい。

### 対応（2026-08-07・対応済）

`cancel()` が偽を返した future（＝既に走っている）を `wait()` で待って
`_collect()` するようにした。`aborted_reason` は
`if reason and not result.aborted` で最初の理由を保つので、中断理由は上書きされない。

テストは `tests/test_executor.py` を新設（`run_session` を差し替えて Spark 抜きで回す）。

- 中断時に走っていたセッションの記録が結果に残ること
- 中断しない経路が壊れていないこと（回帰）

## M5. `finalize_panel()` が候補ゼロのセルを不足として数えない

```python
# persona_sim/panel/build.py:185-211
by_cell: dict[str, list[str]] = {}
for row in candidates:
    by_cell.setdefault(row["cell_id"], []).append(row["persona_uuid"])

for cell_id, uuids in by_cell.items():      # ← 候補があるセルしか回らない
    needed = requested.get(cell_id, 0)
    ...
    if confirmed < needed:
        result.shortfalls[cell_id] = needed - confirmed
```

### なぜ問題か

`by_cell` は `panels` に `role='candidate'` の行があるセルしか持たない。
`requested`（`allocate_cell_sizes()` の結果）にあって候補が1件も無いセルは
ループに入らず、`shortfalls` にも載らない。

```python
@property
def complete(self) -> bool:
    return not self.shortfalls
```

つまり**そのセルが0人でも `complete` が真になる**。`screen_survey()` は

```python
if finalized.complete:
    break
```

で抜け、`finalize_panel()` は `main_panel.unionByName(others)` を書いて
そのセル0人のパネルを確定する。本調査はそのまま走る。

通常は `select_members()` の `_raise_if_short()`（E1）が先に止めるので到達しない。
しかし `screen_survey()` には E1 を握りつぶす経路がある。

```python
# persona_sim/panel/screening.py:673-680
try:
    build_panel(spark, survey, storage, oversample_factor=factor)
except InsufficientCandidatesError:
    # 条件に合うペルソナを使い切った。（中略）今ある候補で判定して結果を返す。
    population_capped = True
```

この判断自体は妥当（「30人頼んだのに480人足りない」という報告を避ける）だが、
握りつぶした先で `finalize_panel()` が0人セルを見逃すと、
**E1 も E2 も出ないまま構成の欠けたパネルで本調査が走る**。

`aggregate` の `panel_composition.csv` にはそのセルが 0 と出るが、
止まらないので気づかずに集計表を読むことになる。

> **到達性の訂正（2026-08-07）**
>
> 上に「E1 を握りつぶす経路から**到達しうる**」と書いたが、修正時に追い直したところ
> **到達経路は無かった。** `select_members()` が全セルで `achieved >= needed` を
> 保証して（満たなければ E1）から `panels` を書くので、`requested` にあるセルは
> 必ず候補を持つ。握りつぶしている E1 は「候補を**増やせ**なかった」場合で、
> 既存の候補は残っている。
>
> したがってこれは live なバグではなく、**充足判定が「候補は必ずある」という
> 前提に黙って依存している**という設計上の弱さ。防御的に直した。

### 修正方針

`requested` を基準にループする。

```python
for cell_id in requested:
    uuids = by_cell.get(cell_id, [])
    ...
```

こうすると候補ゼロのセルは `confirmed == 0 < needed` で `shortfalls` に載り、
既存の `ScreenerShortfallError` の経路（`_shortfall_message()`）に乗る。

`_shortfall_message()` 側も同じ前提を持っている（`for cell_id in finalized.achieved` で
インシデンスを組むので、`achieved` に載らないセルは通過率の行に出ない）ので、
あわせて `requested` 基準に揃える。

### 対応（2026-08-07・対応済）

**割り付けにあるセルを必ず1周する**ようにした。あわせて、割り付けに無いセルの候補
（調査定義を変えた後などに残る）も落とさないよう、`requested ∪ by_cell` を回している——
`requested` だけにすると、そうした行が書き戻されずに**消える**。

```python
for cell_id in [*requested, *(c for c in by_cell if c not in requested)]:
    uuids = by_cell.get(cell_id, [])
    needed = requested.get(cell_id, 0)
```

`_shortfall_message()` は**変更していない**。この修正で `result.achieved` が
全セルを含むようになったため、`for cell_id in finalized.achieved` がそのまま正しくなる。

テストは `tests/test_screening_spark.py` に1件追加（候補ゼロのセルが `shortfalls` に載り
`complete` が偽になること）。手元では Java が無く実行できなかったが、
**CI の `spark-test` ジョブで通過を確認済み**（`test_a_cell_without_candidates_is_reported_as_short`）。

## M6. 集計が O(コンセプト × 設問 × 全回答) で走査する

```python
# persona_sim/aggregate/crosstab.py:277-286
for stimulus in survey.stimuli:
    for question in survey.questions:
        if not is_tabulated(question):
            continue
        subset = [
            answer for answer in answers
            if answer.stimulus_id == stimulus.id and answer.question_id == question.id

```

```python
# persona_sim/aggregate/crosstab.py:310-318
for stimulus in survey.stimuli:
    subset = [answer for answer in answers if answer.stimulus_id == stimulus.id]
    for segment, value, group in group_by_segments(subset, segments):
        for question in tabulated:
            per_question = [a for a in group if a.question_id == question.id]
```

### なぜ問題か

`crosstabs()` はコンセプト × 設問の各組で `answers` を全走査する。
`concept_summary()` はさらに深く、コンセプト × セグメント値 × 設問の各段で走査する。

`aggregate.build_result()` は `crosstabs()` を1回、`concept_summary()` を**2回**
（トップライン用と セグメント別用）呼ぶ。

`frame.py` の docstring は規模をこう見積もっている。

> フェーズ1の想定規模（1,000人 × 10コンセプト × 数問 ＝ 数万行、§12 M7）では問題にならない

「数万行」の見積もりは正しいが、走査回数のほうが効く。
10コンセプト × 10設問 × 5万 `Answer` で `crosstabs()` だけで500万回の比較、
`concept_summary()` はセグメント値の数だけさらに掛かる。

これは Web UI の「データを取得」の待ち時間に直接乗る
（`warehouse.build_result()` が同じ `build_result()` を呼ぶ）。
`docs/issues/20260805004.md` で「調査一覧が出るまで待たされる」への対処として
`runs()` にキャッシュを入れた経緯があるが、こちらは取得のたびに毎回走る。

なお `crosstab.py` は「pyspark に依存しない純関数」という設計方針を持つモジュールで、
その方針は正しい。変えるべきは走査の仕方だけ。

### 修正方針

先頭で索引を1回作る。

```python
def _index(answers: Sequence[Answer]) -> dict[tuple[str, str], list[Answer]]:
    """(stimulus_id, question_id) ごとに畳む。

    表ごとに `answers` を線形走査すると、コンセプト数 × 設問数の回数だけ全件を舐める。
    """
    buckets: dict[tuple[str, str], list[Answer]] = {}
    for answer in answers:
        buckets.setdefault((answer.stimulus_id, answer.question_id), []).append(answer)
    return buckets
```

`concept_summary()` は `stimulus_id` だけの索引も要る（`group_by_segments` に渡す前に絞るため）。

純関数のままなので、`tests/test_aggregate_pure.py` / `tests/test_crosstab.py` の既存テストで
出力が変わらないことを担保できる。挙動を変えないリファクタリングとして扱う。

### 対応（2026-08-07・対応済）

`_by_stimulus()` / `_by_question()` を足し、`crosstabs()` と `concept_summary()` の
線形走査を索引引きに置き換えた。`concept_summary()` はセグメント値ごとにも
設問索引を作り直す（軸を増やすほど二乗で効いていた箇所）。

**挙動不変のリファクタリングなので新規テストは足していない。**
既存の集計テスト（`test_aggregate_pure` / `test_crosstab` / `test_export` /
`test_results_page`）が同じ数字を出し続けることで担保している。

## M7. `infer` の `sessions_skipped` と `sessions_total` の単位が違う

```python
# persona_sim/panel/screening.py:700-706
expected = expected_question_ids(screener)
todo = [...]

```

### なぜ問題か

`expected_question_ids()` は `infer` では `(INFER_QUESTION_ID,)` の1要素を返すので、
`sessions_skipped` は**判定済みペルソナの人数**になる。

一方 `sessions_total` は `_InferExecution` 経由で**バッチ数**が入る。

```python
# persona_sim/panel/screening.py:820-823
"""`infer` は1バッチ＝1呼び出しなので、セッション数はバッチ数で数える。"""
```

CLI は両方を同じ「バッチ」というラベルで並べる。

```python

print(f"{unit}: {result.sessions_ok} 完了 / {result.sessions_total} 中")
if result.sessions_skipped:
    print(f"  うち判定済みでスキップ: {result.sessions_skipped}")
```

`batch_size: 20` で候補400人のうち380人が判定済みなら、

```
バッチ: 1 完了 / 1 中
  うち判定済みでスキップ: 380
```

**1バッチ中1バッチ完了なのに380スキップ**と出る。「うち」と書いてあるので、
総数を超える内訳になっている。

`ask` では `len(expected)` が設問数なので設問単位のセッション数と揃っており、正しい。
`infer` を後から同じ器に載せたときにここだけ揃わなかったもの。

### 修正方針

`infer` はバッチ換算にする。

```python
skipped_personas = len(candidates) - len(todo)
result.sessions_skipped += (
    infer_session_count(skipped_personas, screener) if screener.infers
    else skipped_personas * len(expected)
)
```

`infer_session_count()` は `panel/infer.py:399` にあるので新規に割り算を書かない。
換算は概算になるが（実際のバッチ境界とは一致しない）、`sessions_total` と同じ単位で
「どのくらい省けたか」を示すという用途には足りる。

人数のほうを見せたいなら `personas_skipped` を別フィールドで足し、
CLI で「判定済みの候補: N 名」と単位付きで出す。どちらでもよいが、
**同じラベルで違う単位を並べない**ことが要点。

### 対応（2026-08-07・対応済）

換算を `screening.skipped_session_count()` という純関数に切り出し、
`screen_survey()` はそれを呼ぶだけにした。`infer` はバッチ換算
（`infer_session_count()` を再利用）、`ask` は従来どおり `人数 × 設問数`。

**純関数にしたのはテストのため。** `screen_survey()` は Spark を要求し
この環境では実行できないが、換算の中身はこれで非 Spark に固定できる。
`tests/test_screening.py` に4件追加（`ask` は設問数倍・`infer` はバッチ数・
端数の切り上げ・0件は0）。

`cli.py` の表示は単位が揃うので変更していない。

## L1. `allocate_cell_sizes()` は proportion 合計が1超だと誤配分する

```python
# persona_sim/panel/quotas.py:34-39
remaining = size - sum(allocated.values())
order = sorted(exact, key=lambda cell_id: (-(exact[cell_id] - allocated[cell_id]), cell_id))
for cell_id in order[:remaining]:
    allocated[cell_id] += 1
```

`remaining` が負だと `order[:-3]` のようになり、Python のスライスは
**「末尾3個を除く全部」**を返す。つまり多くのセルに +1 され、合計がさらに増える。
「余りを配る」処理が「余分に配る」処理に反転する。

`validate._check_quotas()` が合計 1.0 を検証するので通常は起きない。
ただし `warehouse.fetch_survey()`（`runs.metadata_json` からの復元）は
`survey_from_dict()` を通すだけで `validate_static()` を呼ばないので、
壊れた定義が保存されていれば Web UI の集計側で到達しうる。

**修正方針**: `remaining = max(0, size - sum(allocated.values()))`。
静かに誤った数字を出すより、配らないほうがまだ読み取れる。

### 対応（2026-08-08・対応済）

方針どおり `max(0, ...)` を入れ、反転の理由（負のスライスが「末尾 n 個を除く全部」を返すこと）と
`warehouse.fetch_survey()` が `validate_static()` を通さないことをコメントに残した。

`tests/test_quotas.py::test_proportion_allocation_does_not_hand_out_extras_when_proportions_exceed_one`
を追加。理論値 4/4/4（計12 > size=10）で「余りが1人も配られない」ことを見る。

## L6. `WorkspaceClient` の遅延生成にロックが無い

## L8. `app.yaml` がカタログ名・スキーマ名を直書きしている

```yaml
# app.yaml:29-33
  # --- 直接書く値。テーブルの置き場所（AGENTS.md によりコードには書かない） ---
  - name: 'PERSONA_SIM_CATALOG'
    value: 'research_system'
  - name: 'PERSONA_SIM_SCHEMA'
    value: 'default'
```

### なぜ問題か

`AGENTS.md:93` はこう定めている。

> - **カタログ名・スキーマ名は書かない。** テーブルの置き場所は環境変数
>   （`PERSONA_SIM_CATALOG` / `PERSONA_SIM_SCHEMA` / `PERSONA_SIM_WAREHOUSE`）からのみ解決する

`persona_sim/config.py` はこれを守っている（環境変数からしか読まない）。
しかし `app.yaml` は**その環境変数に入れる値そのものをリポジトリにコミットしている**ので、
リポジトリを見ればカタログ名が読める。ルールの目的から見ると達成されていない。

`app.yaml` のコメント自身が「AGENTS.md によりコードには書かない」と書いており、
「コードには書かないが app.yaml には書く」という解釈を取っていることが分かる。
この解釈が意図的なのか、なし崩しなのかがコードからは判断できない。

判断材料として、この規則には既に前例のある例外がある。
`CHANGELOG.md` の項目9で **サービングエンドポイント名** が秘密情報の定義から外され、
`AGENTS.md:89` に「秘密ではなく、実際に何で回したかが読み取れないと再現できないため」という
理由つきで明記された。カタログ名についてはそのとき

> カタログ名・資格情報は従来どおり環境変数からのみ読む

と据え置かれている。つまり **`app.yaml` の直書きは、その据え置きと整合していない**。

実害の程度は解釈次第である。`research_system` / `default` は
顧客名でも内部ホスト名でもなく、リポジトリ名と Databricks の既定スキーマ名なので、
漏れて困る情報とは言いにくい。一方でこのリポジトリは
「設定したつもり」と「実挙動」の食い違いを繰り返し戒めており、
**ルールと実態がずれたまま放置されること自体**が問題になる種類のプロジェクトである。

### 修正方針（どちらかを選ぶ）

**案A: 実態に合わせてルールを改める。** `AGENTS.md` に、サービングエンドポイント名と
同じ形の例外を書く。「デプロイ設定（`app.yaml` / Bundle）に置く配置先は秘密ではない。
どのカタログに書いたのかが読み取れないと結果を辿れないため」といった理由を添える。
この場合 `app.yaml` は変更不要で、コメントの文言だけ実態に合わせる。

**案B: ルールに合わせて実態を改める。** `app.yaml` から `value:` を外し、
`valueFrom:` でワークスペースのアプリ設定から注入する（`DATABRICKS_WAREHOUSE_ID` /
`PERSONA_SIM_JOB_ID` / `PERSONA_SIM_SURVEY_VOLUME` が既に取っている形と揃う）。
`deploy/README.md` に設定手順を足す必要がある。

**判断は利用者に委ねる。**「秘密かどうか」ではなく
「デプロイ先が読み取れることに価値があるか」で決めるのが、
エンドポイント名のときと同じ筋になる。どちらを採るにせよ、
`AGENTS.md` と `app.yaml` のどちらかは直す。

### 対応（2026-08-08・対応済／案A）

利用者の判断は**案A（ルールを実態に合わせる）**。`AGENTS.md` の「カタログ名・スキーマ名は
書かない」を「**コードに**書かない」と限定したうえで、サービングエンドポイント名と同じ形の
例外条項を足した——デプロイ設定（`app.yaml` / Bundle）に配置先を書くのは可、
どのカタログに書いたのかが読み取れないと結果を辿れないため。環境変数の値を**入れる**側で
あって、コードから読む側ではないので上の規則と両立する。

`app.yaml` は挙動を変えていない。「AGENTS.md によりコードには書かない」というコメントが
例外条項を指す文言になっていなかったので、そこだけ書き直した。

## L10. 冪等トークンが `survey_id` の一意性に依存している（旧 H5 — **重大度を訂正**）

> **訂正（2026-08-07）**
>
> この所見は当初 **H5（高）** として
> 「同じ `survey_id` は約64日間、二度と実行できない」「失敗した実行の投入し直しで
> **確実に踏む**」と書いていた。**これは誤りだった。**
> 修正に着手する段でコードを追い直したところ、現行フローでは踏まないと分かったため、
> 低へ移し、記述を書き直した。

```python
# persona_sim/uiconfig/jobs.py:75
return f"persona-sim-{survey_id}"
```

### 事実関係

Databricks Jobs API の `idempotency_token` は、一致するトークンの run が既にあれば
新しい run を作らず既存 run の ID を返す（保持は約64日）。ここまでは当初の記述どおり。

**誤っていたのは「同じ `survey_id` で投げ直す場面が普通に起きる」という前提のほう。**

`submit_survey()` の呼び出し元は `app/views/survey_design.py` の1箇所だけで、
渡る `survey_id` は必ず `st.session_state.survey_id` ＝
`uiconfig.build.survey_id()` が作る `{slug}_{時刻}_{secrets.token_hex(3)}`。
投入が成功したら `survey_design.py` が session_state から捨てるので、
**次の投入にはまた新しい ID が振られる**。

つまりトークンは実質「投入1回につき1つ」で、docstring が言う
「ボタンの二度押しや再実行で同じ調査が複数回走る」の抑止は**実際に成立している**
（投入が成功するまで `survey_id` が固定されるため、二度押しは同じトークンになる）。

当初挙げた「踏む経路3つ」を検討し直すと、

1. `form.survey_id` を明示して同じ ID で投入し直す … **これだけが本当**
2. 失敗した実行の投入し直し … 失敗が `run_now` の**前**なら run は作られていないので
   新しい run が立つ。`run_now` の**後**に失敗した場合は既存 run の ID が返るが、
   それは**重複実行を防いだ正しい挙動**
3. 調査定義を直して同じ ID で再投入 … 画面からは ID を固定できないので起きない

### 残るリスク

`SurveyForm.survey_id` は公開フィールドで、呼び出し側が ID を固定できる
（`tests/test_uiconfig.py::test_a_pinned_survey_id_survives_repeated_assembly` が実際に固定している）。
固定した ID で2回投入すると、2回目が**成功と区別がつかないまま空振りする**。
画面以外（ノートブック等）から `submit_survey()` を直接呼ぶ場合も同じ。

**live なバグではなく latent な罠。** 今の呼び出し方に依存して成立している、というのが正確。

### 当初案（nonce を混ぜる）を採らない理由

当初は `idempotency_token(survey_id, nonce)` にして
`st.session_state` の UUID を渡す案を書いた。**これは採らない。**

現行の `survey_id` が既に「投入1回＝1値」なので nonce を足しても得るものが無く、
逆に **nonce の寿命を誤ると今効いている二度押し防止を壊す**
（スクリプト再実行のたびに変わる nonce にすると、ボタンを2回押したぶん2回走る）。

### 対応（2026-08-07）

**挙動は変更していない。** `idempotency_token()` の docstring に
「`survey_id` が投入ごとに一意であることに依存している」ことと、
ID を固定する経路を足すときは併せて見直す旨を明記した。

固定 ID の空振りまで塞ぐなら `jobs.run()` に `nonce` 引数を足し、
画面が session_state の値を渡す（成功時に捨てる）形になる。
現行の二度押し防止は維持されるが、差分は増える。**未着手。**

**修正方針**: 先頭で `cd "${CLAUDE_PROJECT_DIR:-$PWD}"` を行う。
`CLAUDE_PROJECT_DIR` はフックに渡される環境変数。

## R2. `link-repo.sh` が既配線を二重に追記しうる

```bash
# scripts/link-repo.sh:27
if [ -f CLAUDE.md ] && grep -qF "$MARKER" CLAUDE.md; then
```

判定はマーカー `<!-- shared-knowledge:import -->` の有無だけ。
retrospective 自身の `CLAUDE.md` は**マーカー無しで**
`@~/.claude/shared/rules/{common,git,coding}.md` の3行を持っているので、
ここで `link-repo.sh` を実行すると import が重複して追記される。

`@import` が重複しても Claude Code 側は同じファイルを2回読むだけで壊れはしないが、
「冪等: 既に配線済みなら二重登録しない」という docstring の保証が成立していない。

（当リポジトリの `CLAUDE.md` にはマーカーがあるので、こちらは冪等に動く。）

**修正方針**: マーカーに加えて `@~/.claude/shared/rules/common.md` の存在でも
既配線とみなす。ついでにマーカーだけを追記して以後の判定を揃える手もある。

## R3. 毎セッション `git pull` にタイムアウトが無い

```bash
# hooks/session-start.sh:26 付近
git -C "$SHARED_DIR" pull --ff-only --quiet 2>/dev/null \
  && echo "..." >&2 || echo "[retrospective] git pull に失敗(オフライン?)..." >&2
```

オフライン時に `||` でフォールバックする設計は正しいが、
**応答が返らない場合**（VPN 越し・DNS が遅い・認証待ち）は待ち続ける。
セッション開始が毎回そのぶん遅くなる。

**修正方針**: `timeout 10 git -C "$SHARED_DIR" pull ...` で頭打ちにする。
`timeout` が無い環境（macOS の素の環境など）を考えるなら
`command -v timeout` で分岐する。

# 補足：見て問題が無かったもの

同じ場所を再度調べる手間を省くため、確認して問題が無かった点を残す。

- **`presented_options()` の決定論性** — `sha256(seed|persona_uuid|question_id)` から
  `random.Random` を作って `order` をシャッフルする。同じ入力で必ず同じ順序。
  `options_order` は「提示順に並べた定義順番号」で、`to_defined_codes()` の
  `order[code - 1]` と整合している
- **`assignment_table()` の round-robin** — `cell_rank % K` で巡回窓を取るので
  コンセプトごとの評価者数の差は最大1。`rotation: random` の並べ替えも
  `sha2(persona_uuid|seed|stimulus)` の昇順で決定論的（`F.shuffle` を避けた理由も明記済み）
- **`select_members()` の抽出コスト** — `docs/history/20260806-030737-*` で
  指数的な再計算を解消済み。`pool.cache()` と `try/finally` の `unpersist()`、
  除外集合の作り直しがいずれも入っている
- **`read_screener_codes()` の `judge_error` 除外** — 判定失敗行を返さないので、
  通信失敗が「非通過」として居座らない。`flags` が null の古い行を落とさない配慮もある
- **`screening_fingerprint()` の対象** — `oversample_factor` と `concurrency` を
  含めない判断が正しい（含めると再試行のたびに全件を聞き直す）
- **`_content_to_text()`** — content part 配列を `str()` に通す穴が塞がれており、
  1文字も取れなければ repr にフォールバックせず失敗させる
- **`_to_completion()` の判定順** — `finish_reason == "length"` を
  `content is None` より前に見る。理由もコメントに残っている
- **`warehouse.py` のパラメータ化** — 値はすべて名前付きパラメータ。
  文字列連結で SQL を組む箇所は無い。配列カラムを `to_json` で受ける判断の理由も明記
- **`delta.delete_survey_rows()`** — 述語を `F.col(...) == F.lit(...)` で組むので
  `survey_id` に引用符が入っても壊れない
- **資格情報** — トークン・ワークスペース URL・内部ホスト名の直書きは無い。
  認証は SDK の既定チェーンに委ねられている（`llm/databricks.py` /
  `storage/warehouse.py::connect()`）。`.gitignore` も `.databrickscfg` / `*.pem` /
  `*.key` / `secrets/` を落としている
  （カタログ名・スキーマ名については L8 を参照）
