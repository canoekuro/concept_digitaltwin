## 2つの方式

LLM ペルソナでは対象者条件の満たし方が2通りある。**費用と、得られるものが違う。**

| | `ask`（実際に聞く） | `assume`（前提として与える） |
|---|---|---|
| 費用 | `size × oversample_factor × 設問数` | **0** |
| インシデンス | **実測できる** | **測れない**（`null` を記録） |
| パネル構成 | セル内で条件該当者に偏る | 割り付けどおりのまま行動だけ付与 |
| 内的整合性 | 本人の記述と矛盾しない | **ナラティブと矛盾しうる** |

どちらが正しいというものではなく、答えている問いが違う。`ask` は「条件該当者はどう反応するか」、
`assume` は「割り付けどおりの構成の人が、その行動を持つとしたらどう反応するか」。

## 設計判断

### 1. 2方式とも「ペルソナカードの前提ブロック」に集約する

`ask` の「回答をコンテキストとして持たせ続ける」は会話履歴では実現できない。
既定の `memory: none` では設問ごとに独立したセッションになるため履歴が残らない。

そこで両方式とも、確定したペルソナのカード末尾にブロックを足す。見出しで由来を分ける
（【調査前の確認】= 本人の回答 / 【前提】= こちらが与えた条件）。こうすると `memory` の
設定によらず前提が効き、2方式の違いは文言の由来だけになる。

`ask` の文言は「`label`（無ければ設問文）: 選択した選択肢」で機械的に作る。
言い換えを挟むと、本人が答えていない内容を混ぜてしまう。
`assume` の `premise` は自動生成しない。何を前提にしたかは書いた本人の言葉で残す。

### 2. 確定後に `cell_rank` を振り直してから割り当てる（最重要）

`sample_overlap: disjoint` のセル内 round-robin は `cell_rank` を起点にしている。
オーバーサンプルした順位のまま割り当てて非通過者を落とすと、コンセプトごとの
評価者数が崩れる。確定した `main` だけを 0〜n-1 で振り直してから割り当てる。

### 3. 不足時の再試行は「順位の先を伸ばす」だけで済む

抽出はハッシュ順なので、`n × factor` を増やすことは同じ並びの先頭を伸ばすことと同じ。
判定済みの候補はそのまま残り、増えた分だけ追加でスクリーニングすればよい。

### 4. インシデンスは `panels` から計算する

`(main + reserve) / (main + reserve + screened_out)`。新しいテーブルを増やさない。
**`assume` では `null`。1.0 と書かない**（測っていないことと、全員該当は違う）。
