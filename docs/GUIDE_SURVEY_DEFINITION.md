# 調査定義の書き方

調査定義は **YAML 1ファイル**で、これがシステムへの唯一の入力です。パネル構築から
集計まで、すべてこのファイルの内容だけで決まります。

この文書は**書き方**だけを扱います。なぜその設計なのかは `SPEC.md` にあります
（各節からリンクします）。フィールドの網羅的な一覧も `SPEC.md` §3 です。

**書いたら必ず検証を通してください。** 綴り違い・未知のキー・設問の抜けは、実行前に
ここで止まります。直し方もメッセージに出ます。

```python
from persona_sim.panel.loader import load_survey
from persona_sim.panel.validate import validate_static

report = validate_static(load_survey("path/to/survey.yaml"))
```

## 1. 最小の調査定義

コンセプトを1件見せて1問聞くだけの形です。ここに足していきます。

```yaml
survey:
  id: "cs_2026_0801_minimal"     # 英数字と _ のみ。テーブルのパーティション値になる
  name: "最小サンプル"

panel:
  size: 10
  seed: 42                        # 同じ seed なら誰を抽出するかまで再現される
  quotas:
    mode: "count"                 # count（人数）| proportion（比率）
    cells:
      # 合計は panel.size と一致させること（ずれると validate が止まる）
      - {cell_id: "M_20_40s", sex: "男", age_min: 20, age_max: 49, n: 5}
      - {cell_id: "F_20_40s", sex: "女", age_min: 20, age_max: 49, n: 5}

stimuli:
  - id: "c1"
    name: "ゆずハイボール"
    text: |
      【商品名】ゆずハイボール
      【特徴】国産ゆず果汁を使った、甘さ控えめの缶ハイボール。アルコール5%。
      【価格】希望小売価格 205円（350ml）

questions:
  - id: "q_intent"
    text: "この商品を購入したいと思いますか。"
    type: "single"
    options:
      - "ぜひ購入したい"
      - "やや購入したい"
      - "どちらともいえない"
      - "あまり購入したくない"
      - "まったく購入したくない"
    top_box: [1, 2]               # T2B に数える選択肢番号（定義順）

main_survey:
  model:
    endpoint: "fake"              # fake（ダミー）| databricks
    deployment: "smoke_test"
```

`design` を省略すると **`sample_overlap: same` × `presentation: sequential`** になります
（`SPEC.md` §5.3）。コンセプトが1件なら、これは「全員が1案を評価する」形です。

## 2. 設問の書き方

### 設問はコンセプトごとに展開する

**`questions` はコンセプトに繰り返し適用されるテンプレートではありません。** 各設問は
`slot`（そのペルソナが**何番目に見るコンセプト**について聞くか）に紐づき、1人が評価する
コンセプトの数だけ並べます。

コンセプトが1件（または `sample_overlap: disjoint`）なら `slot` は省略できます。上の最小例が
それです。2件以上を1人に見せるなら、その数だけ書きます。

```yaml
survey:
  id: "cs_2026_0801_two_concepts"
  name: "2案の比較"

panel:
  size: 10
  seed: 42
  quotas:
    mode: "count"
    cells:
      - {cell_id: "M_20_40s", sex: "男", age_min: 20, age_max: 49, n: 5}
      - {cell_id: "F_20_40s", sex: "女", age_min: 20, age_max: 49, n: 5}

stimuli:
  - {id: "c1", name: "案A", text: "ゆず果汁の缶ハイボール。205円。"}
  - {id: "c2", name: "案B", text: "無糖レモンサワー。190円。"}

questions:
  # --- 1番目に提示する案について ---
  - id: "q_intent_1"
    slot: 1
    measure: "q_intent"           # コンセプト横断で「同じ問い」として束ねるキー
    text: "この商品を購入したいと思いますか。"
    type: "single"
    options: ["ぜひ", "やや", "どちらとも", "あまり", "まったく"]
    top_box: [1, 2]

  # --- 2番目に提示する案について ---
  - id: "q_intent_2"
    slot: 2
    measure: "q_intent"           # 上と同じ measure。だから1つの比較表に並ぶ
    text: "この商品を購入したいと思いますか。"
    type: "single"
    options: ["ぜひ", "やや", "どちらとも", "あまり", "まったく"]
    top_box: [1, 2]

main_survey:
  model: {endpoint: "fake", deployment: "smoke_test"}
```

**`measure` を忘れないでください。** これが無いと `q_intent_1` と `q_intent_2` が別の指標として
集計され、コンセプト比較表がコンセプトごとにばらけます。`measure` を揃えた設問どうしは
`type` / `options` / `top_box` が一致している必要があります（違うと `validate` が止めます。
T2B を代表1つの定義で全コンセプトぶん計算するためです）。

> **Web UI 経由なら展開は不要です。** 画面で設問を1組だけ作れば、`uiconfig/build.py` が
> コンセプト数ぶんに展開して `measure` も付けます。この節は調査定義を直接書く場合の話です。

### 設問タイプ

| `type` | 用途 | `options` | 備考 |
|---|---|---|---|
| `single` | 単一回答 | 必須（2つ以上） | |
| `multi` | 複数回答 | 必須（2つ以上） | 比率の合計は100%を超える |
| `scale` | 尺度 | 必須（5 / 7 / 10 段階など） | **順序尺度**。シャッフル禁止 |
| `open` | 自由回答 | 書けない | `max_length` で字数を指定 |
| `numeric` | 数値回答 | 書けない | 平均だけ出す |

`rank` / `maxdiff` / コンジョイントはフェーズ1では非対応です（指定すると止まります）。

### 選択肢のシャッフル

`randomize_options: true` で、**人ごとに**選択肢の提示順を変えられます。順序は
`seed` × `persona_uuid` × 設問ID から決まるので、何度実行しても同じです。実際に見せた順は
`options_order` に記録され、集計時に定義順へ戻されます。

**順序尺度には使えません。** `type: scale` の設問、および `top_box` を持つ設問は順序尺度と
みなされ、`randomize_options: true` を書くと `validate` が止めます。並び自体が意味を持つので、
混ぜると尺度が壊れるためです。

飲用シーン・ブランド・購入理由のように**並びに意味がない選択肢**で使ってください。

### 設問ごとにシステムプロンプトを変える

聞いていることの性質が設問で違うなら、`[system]`（なりきりの指示）も分けられます。
購入意向は「自分の金で買うか」、新規性は「既存品と何が違うか」を判断させる問いで、
1本の指示で兼ねるより書き分けたほうが精度が高くなります。

`main_survey.prompt.systems` に**名前を付けて**並べ、設問の `system` でその名前を指します。

```yaml
survey:
  id: "cs_2026_0801_two_systems"
  name: "設問ごとにシステムプロンプトを変える例"

panel:
  size: 10
  seed: 42
  quotas:
    mode: "count"
    cells:
      - {cell_id: "M_20_40s", sex: "男", age_min: 20, age_max: 49, n: 5}
      - {cell_id: "F_20_40s", sex: "女", age_min: 20, age_max: 49, n: 5}

stimuli:
  - id: "c1"
    name: "ゆずハイボール"
    text: "【商品名】ゆずハイボール／【価格】205円（350ml）"

questions:
  - id: "q_intent"
    system: "purchase_intent"       # systems の名前。文面は書かない
    text: "この商品を購入したいと思いますか。"
    type: "single"
    options: ["ぜひ購入したい", "やや購入したい", "どちらともいえない", "あまり購入したくない", "まったく購入したくない"]
    top_box: [1, 2]
  - id: "q_novelty"
    system: "novelty"
    text: "この商品は新しいと思いますか。"
    type: "single"
    options: ["とても新しい", "やや新しい", "どちらともいえない", "あまり新しくない", "まったく新しくない"]
    top_box: [1, 2]
    remember: ["q_intent"]          # 記憶は跨いでよい（下記）
  - id: "q_reason"
    text: "そう思った理由を教えてください。"   # system 省略＝既定の prompt.system で聞く
    type: "open"
    max_length: 150
    remember: ["q_intent", "q_novelty"]

main_survey:
  model:
    endpoint: "fake"
    deployment: "smoke_test"
  prompt:
    system: |
      あなたはこれから提示する人物になりきって、調査に回答します。
      - 指定された形式のみで回答し、説明や前置きは書かないでください
    systems:
      purchase_intent: |
        あなたはこれから提示する人物になりきって、調査に回答します。
        - この人物のふだんの買い物の仕方・支払える金額に照らして、実際に手に取るかで判断してください
        - 指定された形式のみで回答し、説明や前置きは書かないでください
      novelty: |
        あなたはこれから提示する人物になりきって、調査に回答します。
        - すでに知っている商品と引き比べて、どこが違うのかで判断してください
        - 買いたいかどうかは考えないでください
        - 指定された形式のみで回答し、説明や前置きは書かないでください
```

**設問には文面ではなく名前を書きます。** 設問はコンセプトの数だけ展開されるので、
文面を直書きすると同じ長文が展開数ぶん複製され、直すときに取りこぼすと案によって
違うプロンプトで聞いたことになります。

**`systems` に無い名前を指すと読み込みが止まります。** 綴り違いが黙って既定に落ちると、
書き分けたつもりの設問が既定の `[system]` で聞かれてしまうためです。逆に、書いたのに
どの設問からも指されていない `systems` は `validate` が警告します。

**記憶（`remember`）と併用できます。** そのとき `[system]` に載るのは**いま聞いている
設問のもの**です。上の例では、購入意向の Q&A を持ったまま、新規性用の指示で新規性を聞きます。

> **Web UI 経由なら設定済みです。** 既定の2問（購入意向・新規性）には
> `config/ui_config.yaml` で別々の `[system]` が紐づいています。この節は調査定義を
> 直接書く場合の話です。

## 3. 記憶（`remember`）

各設問に「この設問に答えるとき、どの設問の記憶を持っているか」を書けます
（`SPEC.md` §5.1）。**書かなければ何も覚えません。**

| 書き方 | 意味 |
|---|---|
| 省略 / `remember: "none"` | 何も覚えていない状態で答える |
| `remember: ["q_intent_1"]` | 列挙した設問の Q&A を持ったまま答える |
| `remember: "all"` | それまでに聞いた設問すべて（**コンセプトをまたぐ**） |

### 何が起きるか

覚えている設問のやりとりが、**会話履歴としてそのまま積まれます**。要約でも引用でもなく、
モデルから見れば自分がさっき答えた会話の続きです。

```
[system]    なりきり指示
[user]      プロフィール + 提示物 + 購入意向の設問（選択肢つき）
[assistant] 1                        ← 1問目でモデルが返した文字列そのまま
[user]      ■設問 そう思った理由を教えてください。
```

プロフィールは先頭に1回だけ、コンセプトの提示文もその会話で初出のときだけ載ります。

### 使いどころ

**同じコンセプトの中**では有用です。「購入意向 → その理由」は、意向を知らずに理由を
書かせても意味を成しません。

```yaml
- id: "q_intent_1"
  slot: 1
  measure: "q_intent"
  # remember を書かない = 記憶なし
- id: "q_reason_1"
  slot: 1
  measure: "q_reason"
  type: "open"
  max_length: 150
  remember: ["q_intent_1"]      # 購入意向の回答を踏まえて理由を書かせる
```

**コンセプトをまたぐ記憶は、比較を歪めます。** 案Aの評価が案Bの回答に混ざるので、
案どうしを公平に比べたいなら入れないでください。既定（何も書かない）が
**反実仮想モナディック**で、実査では不可能な「同じ人に、前の記憶なしで別の案を聞く」形です。
順序効果が原理的に発生しないのが利点です（`SPEC.md` §5.3）。

### 細かい規則

- **列挙どおりで推移しません。** Q4 が Q3 を、Q3 が Q1 を覚えていても、Q4 が見るのは Q3 だけ。
  Q1 も要るなら Q4 に両方書きます
- 再生される順は書いた順ではなく**聞いた順**（`slot` 昇順・記述順）です
- **まだ答えていない設問は参照できません**（`validate` が止めます）
- 飛ばし越しできます。`remember: ["q1", "q2"]` と書けば、間の `q3` は入りません

### 費用への影響

記憶を繋いでも **API 呼び出しの回数は変わりません**（設問の数だけ呼びます）。変わるのは
2つです。

- **送信トークンは増えます。** 前の設問と回答を毎回積み直すため
- **並列度は落ちます。** 記憶で繋がった設問は逐次に実行され、途中で失敗すると
  その塊を丸ごとやり直します

`validate` が出す「本調査 : N セッション」は**呼び出し回数ではなく、並列に流せる単位の数**です。

## 4. 理由を書かせる（`reasoning`）

選択式の設問で、**理由を書いてから番号を選ばせる**設定です（`SPEC.md` §6.3）。
構造化出力のスキーマに `reasoning` を足し、番号より**前**に置くことで実現しています。
生成は前から進むので、順序がそのまま「考えてから答える」順になります。

書いた理由は `responses.answer_reasoning` に残り、ローデータのダウンロードにも出ます。

```yaml
survey:
  id: "cs_2026_0801_reasoning"
  name: "理由を書かせる例"

panel:
  size: 10
  seed: 42
  quotas:
    mode: "count"
    cells:
      - {cell_id: "M_20_40s", sex: "男", age_min: 20, age_max: 49, n: 5}
      - {cell_id: "F_20_40s", sex: "女", age_min: 20, age_max: 49, n: 5}

stimuli:
  - id: "c1"
    name: "ゆずハイボール"
    text: "【商品名】ゆずハイボール／【価格】205円（350ml）"

questions:
  - id: "q_novelty"
    text: "この商品は新しいと思いますか。"
    type: "single"
    options: ["とても新しい", "やや新しい", "どちらともいえない", "あまり新しくない", "まったく新しくない"]
    top_box: [1, 2]
    reasoning: true                # 既定は false
    reasoning_max_length: 80       # 既定 80。指示行の {max_length} に入る

main_survey:
  model:
    endpoint: "fake"
    deployment: "smoke_test"
    max_tokens_reasoning: 512      # 理由の散文を返させるので max_tokens では足りない
    structured_output: "always"    # reasoning を使うなら必須（下記）
  prompt:
    rules:
      # reasoning: true の設問だけで使う指示行。設問タイプごとに書く（省略時は既定）
      reasoning:
        single: "まず、そう考えた理由を{max_length}文字以内で書き、そのうえで当てはまる番号を1つ選んでください。"
        scale: "まず、そう考えた理由を{max_length}文字以内で書き、そのうえで当てはまる番号を1つ選んでください。"
        multi: "まず、そう考えた理由を{max_length}文字以内で書き、そのうえで当てはまる番号をすべて挙げてください。"
```

### 決まりごと

- **`model.structured_output: "always"` が必須です。** 書かないと `validate` が止めます。
  構造化出力が使えないときのフォールバック（正規表現パース）は最初に現れた数字を
  回答として採るので、**理由の文中の数字を回答にしてしまう**ためです
- 書けるのは `single` / `scale` / `multi` だけです。`open` / `numeric` は本文そのものが
  回答なので、理由を分ける意味がありません
- 指示行は設問タイプのもの（`rules.single` の「番号のみで答えてください。」）を、
  **`rules.reasoning` の同じ設問タイプの行で置き換えます**。併記すると矛盾するためです
- **置き換えなので、設問タイプ固有の指示は `rules.reasoning` 側にも書いてください。**
  `reasoning` を1本の文で書けないのはこのためです。共通の1文にすると `multi` の
  「すべて」が消え、複数回答なのに1つだけ選ばせる問いになります
  （1本の文で書いた旧形式は `validate` が書き方を添えて止めます）

### 字数（`reasoning_max_length`）と予算（`max_tokens_reasoning`）は別物

紛らわしいので明記します。**二重管理ではありません。**

| | `questions[].reasoning_max_length` | `model.max_tokens_reasoning` |
|---|---|---|
| 単位 | 文字 | トークン |
| 相手 | **モデルへの指示**（「80文字以内で書き」） | **エンドポイント側の打ち切り** |
| 強さ | 目安。超えることがあります | 絶対。ここで切れます |
| 書く場所 | 設問ごと | モデルごと（調査で1つ） |

片方から他方を自動計算していないのは、**文字とトークンの比がモデルとトークナイザで
変わる**からです。係数を実装に埋めると、ずれたときに設定からは読み取れなくなります。

予算が足りないと黙って壊れはしませんが、`llm/budget.py` が予算を広げて再送するぶん
呼び出しが増え、天井（4096）まで届かなければ理由が切り詰められて `output_limit`
フラグが付きます。噛み合っていない組み合わせは **`validate` が `W_OUTPUT_BUDGET` で
警告します**（目安は「文字数 × 1.5 + 器のぶん」。推定なので止めはしません）。

自由回答の `max_length` と `model.max_tokens_open` もまったく同じ関係です。

### 集計・フラグへの影響

- `refusal` フラグの判定から**理由の本文は除きます**。こちらが書かせた散文なので、
  「わかりません」「判断できません」が拒否の目印になりません（購入意向の選択肢に
  「わからない」がある以上、言い換えとして高頻度で出ます）。本当の拒否は番号が
  取れないので `parse_error` で表面化します
- クロス集計・T2B は番号だけを使うので変わりません。理由は自由回答表には出ず、
  `answer_reasoning` 列として生データに残ります

### 使うかどうかの判断

**回答が収束してペルソナ間のばらつきが縮む可能性があります**（`SPEC.md` §13 が
思考モードを禁じているのと同じ理由）。`validate` も警告を出します。コンセプト調査の
出力は個人の回答品質ではなく**分布**なので、次を必ず見比べてください。

- T2B・平均スコアの水準だけでなく、**案どうしの順位**
- 選択肢の分布の形（「どちらともいえない」への集中度）とペルソナ間の分散
- 性年代セグメント間の差が残っているか（潰れていたら収束のサイン）
- 出力トークンと所要時間（番号だけの調査より数倍になります）

理由を残したいだけなら、**自由回答の設問を分けて置き、`remember` で繋ぐ**書き方もあります
（§3）。設問が1つ増えて並列度は落ちますが、選択式の回答そのものには手を入れません。

## 5. 対象者条件（スクリーニング）

`screening` は任意です。書かなければ割り付けどおりのパネルをそのまま使います。

**方式は1つです**（`SPEC.md` §4.2）。対象者条件を自然言語で書くと、判定用の LLM が
候補をまとめて読み、条件に合致する蓋然性が高い人にだけ属性を与えます。費用は
`候補数 ÷ batch_size` 回です。

```yaml
screening:
  oversample_factor: 4            # 候補の抽出倍率
  batch_size: 20                  # 1回の判定に渡すペルソナ数
  conditions:
    - "缶チューハイ・缶ハイボールを月1回以上飲む"
```

**選択肢や `pass_if` は書けません。** 本人に選択肢を見せて答えさせないので、書いても
使い道がありません。条件をどう結合するか（すべて満たすのか、いずれかで足りるのか）は
`screening.prompt.rule` の文面に書きます。

**通過率は推定値です。** 本人には聞いていないので実測はできません。
`runs.screener_incidence_estimated` に別枠で記録し、判定結果には `inferred` フラグが
立ちます。実査のインシデンスと同じものとして読まないでください。

確定したペルソナのカード末尾には前提ブロックが付きます。**記憶を持たない設問では会話履歴で
前提を引き継げない**ので、カードに載せることで必ず効かせています。

---

## 6. 提示設計

**反実仮想モナディック固定です**（`SPEC.md` §5）。書く項目はありません。

- 全ペルソナが**全コンセプトを定義順に1件ずつ**評価します
- 同じ人に同じコンセプトが2回当たることはありません
- 設問どうしは既定で独立（`remember` を書かないかぎり記憶を持たない）なので、
  案を独立に評価させたうえで直接比べられます
- 有効サンプル数は `panel.size` のままです

したがって**設問は案の数だけ `slot` 展開が要ります**（コンセプト3件なら slot 1〜3）。
抜けると読み込みで止まります。

---

## 7. よくある止まり方

`validate` と読み込みが止める代表的なものです。**どれもメッセージに直し方が入っています。**

| 症状 | 原因 |
|---|---|
| `割り付けの合計 N が panel.size と一致しない` | `quotas.cells` の `n` の合計を `panel.size` に合わせる |
| `slot [2] の設問が無い` | コンセプト2件目について聞く設問を書いていない |
| `slot は 1〜N。範囲外の slot がある` | コンセプトを減らしたのに設問の展開を直していない |
| `設問IDが重複している` | 展開した設問に同じIDを付けている |
| `measure の設問で top_box が違う` | 同じ問いなのに T2B の定義がコンセプトごとにずれている |
| `順序尺度の選択肢はシャッフルしない` | `scale` / `top_box` を持つ設問の `randomize_options` を外す |
| `未知のキー` | 綴り違い。黙って捨てないので必ず止まります |

## 8. 実行

`notebooks/run_survey.ipynb` を上から実行します（Databricks ジョブの本体でもあります）。

```python
survey = load_survey("survey.yaml")
validate_static(survey)                    # 検証と見積もり（必ず先に）
build_panel(spark, survey, storage)        # パネル構築
screen_survey(spark, survey, storage)      # スクリーニング（screening: を書いたときだけ）
run_survey(spark, survey, storage)         # 回答生成
aggregate_survey(spark, survey, storage, output_dir())  # 集計と出力
```

`validate_static()` は実行前に見積もりを出します。**費用に直結するので必ず確認してください。**

```
パネル人数        : 600
コンセプト数      : 3
1人あたり評価数   : 3
設問数            : 9（別々の問い 3 種）
本調査            : 1,800 セッション
有効サンプル数/案 : 600
```

「設問数 9」は**展開後の延べ数**です。別々の問いは3種で、それが3案ぶんに展開されています。
