## 1. 変更内容

### スクリーニングの結果にトークンを載せた

`ScreeningResult` に `input_tokens` / `output_tokens` を足し、`screen_survey()` が
セッション数を足し込んでいる箇所で一緒に加算するようにした。**中断の early return より
前**に置いてあるので、判定が全滅して中断した場合でも呼んだぶんは計上される。オーバー
サンプルの再試行でこの箇所を複数回通るため `+=` にしている。

判定済みで聞き直さずに早期 return する経路と、`assume` / スクリーナー無しは 0 のまま。
この実行では呼んでいないので正しい。

### `infer` は呼び出し単位で数えた（レコード合算は誤り）

`mode: infer` は1バッチ＝1呼び出しだが、`_to_record()` が候補1人につき1行を作り、その
全行に同じバッチのトークン数を載せている。回答生成側と同じ「レコード単純合算」をここに
持ち込むと、1回しか呼んでいないのに `batch_size` 倍（`app/config/ui_config.yaml` の設定値
では30倍）の数字が出る。`InferResult` にトークンを持たせ、`run_inference()` のバッチ
受け取り箇所で足すようにした。理由はコードのコメントにも残した。

`_InferExecution` は `ExecutionResult` と同じ属性名でトークンを持つ。呼び出し側
（`screen_survey`）は `ask` と `infer` を1本の経路で扱えるまま変わらない。

### 合算ロジックの置き場所を1つにした

`ExecutionResult` に `input_tokens` / `output_tokens` プロパティを足し、
`run/run.py` の `_summarize()` にあった同じ式をそれに置き換えた。挙動は変わらない。
`ask` とサーベイ本体は1レコード＝1呼び出しなので合算で正しい。

### ノートブックの末尾に2セル追加

markdown（範囲の説明）と code（表）を `write_metadata` のセルの後ろに足した。

```
区分                      入力          出力
--------------------------------------------
スクリーナー         1,234,567        89,012
回答生成            45,678,901     2,345,678
--------------------------------------------
合計                46,913,468     2,434,690

※ この実行で呼び出したぶんのみ（再開でスキップしたセッション、判定済みで聞き直さなかった候補は含まない）
```

日本語の見出し・ラベルは等幅表示で2桁を占めるため、`str.ljust` 系の桁数指定では列がずれる
（区分ごとに文字数が違うので行ごとに幅が変わる）。`unicodedata.east_asian_width` で表示桁を
数えて揃えた。金額換算は載せていない。

## 2. 集計範囲について

**この実行で呼び出したぶんだけ**を数える（`run_metadata.json` の `tokens_scope: "run"` と
同じ範囲）。調査全体の累計を `screener_responses` / `responses` から出す案も検討したが、
上記のとおり `infer` のスクリーナー行はバッチのトークンが人数ぶん重複しており、行を識別
する列が無いため正しく重複排除できない。テーブルを読まない設計にして回避した。保存形式は
変えていない（列を足すと既存テーブルの移行が要るため、必要になれば別途）。
