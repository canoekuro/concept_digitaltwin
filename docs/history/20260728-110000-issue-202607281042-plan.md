# 計画: docs/issues/202607281042.md への対応

- **日時**: 2026/07/28 11:00
- **対象**: `persona_sim/llm/databricks.py` / `notebooks/quickstart.ipynb`
- **完了条件**: 自由回答に本文が入り、quickstart がスクリーニングを含む1本の流れになる

## 1. 目的

`docs/issues/202607281042.md` に挙がった2件を解消する。

1. `databricks-gemini-3-5-flash-lite` で回すと `q_reason` の `answer_text` に本文ではなく
   `[{'type': 'text', 'text': '…', 'thoughtSignature': '…'}]` という Python のリスト repr が入る。
2. `notebooks/quickstart.ipynb` はスクリーニングが末尾（`## 15.`）に置かれている。
   「調査の流れを一通り再現する」というこのノートブックのコンセプトに反する。
   スクリーナーの定義は手順6（ジョブ定義）で、実行は手順8（panel）と手順9（run）のあいだで行われるべき。

## 2. 現状分析

### 2.1 content ブロックが repr のまま流れる

`persona_sim/llm/databricks.py` の `_to_completion()` が `text=str(content)` としている。
OpenAI 互換レスポンスの `message.content` は**文字列とは限らず**、Gemini 系エンドポイントは
content part の配列を返す。`str()` はそれを Python のリテラル表記に落とすだけで、
`Completion.text` → `answer_raw` → `parse_answer()` → `answer_text` と流れる。

自由回答が読めなくなるだけでは済まない。構造化出力が使えず正規表現フォールバックに落ちた
選択式では、`_extract_single_code()` の `re.search(r"\d+")` が `thoughtSignature` の base64 に
含まれる数字を拾い、無関係な番号を `answer_code` に入れる。`out_of_range` が立つとも限らない。

`tests/` に LLM クライアントのテストが1件も無く、この経路は一切覆われていない。

### 2.2 スクリーニングが末尾にある

- `persona_sim/panel/screening.py` の `screen_job()` は、スクリーナーが無い場合も `assume` の
  場合も何もせず結果を返す。
- `persona_sim/run/run.py` は、スクリーナーが `ask` なのに `screen` 未実行だと明示的に止める。

つまり `validate → panel → screen → run` は**常に書ける**。対象者条件の有無でノートブックを
分ける必要はなく、末尾に別立てにしておく理由が無い。

### 2.3 作業ブランチのベースが古い

`claude/docs-issues-review-2drsf1` は `90a9a92`（M1 のみの別実装）の上にあり、`origin/main` の
履歴に含まれない。ワークツリーに `notebooks/` も `persona_sim/llm/` も無い状態だった。

## 3. 提案変更

### 3.0 ブランチを `origin/main` へ載せ替える

`git rebase --onto origin/main 90a9a92` で issue ファイルの2コミットだけを載せ替える。
`90a9a92` は main 側の M1〜M6 に置き換えられた並行実装なので持ち込まない。

### 3.1 content ブロックを本文に正規化する（`persona_sim/llm/databricks.py`）

純関数 `_content_to_text()` / `_part_text()` を追加し、`_to_completion()` の `str(content)` を
置き換える。

| 入力 | 扱い |
|---|---|
| `str` | そのまま（挙動を変えない） |
| `list` | 各 part の `text` を順に連結。`type` が `text` か、`type` を持たないものだけ |
| `dict` | 同上を1件に適用 |
| 上記で1文字も取れない | `LLMError`。**repr にフォールバックしない** |

**境界で直す。** パーサ側で防御すると `answer_raw` は壊れたまま残り、スクリーニングの
判定経路にも同じ穴が残る。`Completion.text` がプレーンテキストであることは
`persona_sim/llm/client.py` が定めた契約で、破っているのは Databricks アダプタだけ。

新規 `tests/test_databricks_client.py`（pyspark 非依存）で、素の文字列・issue の実データ形・
複数 text part・text part 無し・`usage`/`model` の取り回しを覆う。

### 3.2 スクリーニングを本流に組み込む（`notebooks/quickstart.ipynb`）

| | 現状 | 変更後 |
|---|---|---|
| 6 | ジョブ定義 | ジョブ定義（**スクリーナーを含む**） |
| 8 | panel | panel（`ask` では候補を引く） |
| — | — | **9. screen（新規）** |
| 9〜14 | run〜再開確認 | 10〜15 |
| 15 | スクリーニング | **削除**（6 と 9 に配分） |

- ジョブ定義を1本にまとめ、`panel.screener` を `mode: "ask"` で持たせる。方式は
  インシデンスを実測できる `ask` を既定にし、`assume` への切り替えは markdown の
  差分コード片で示す（セルを増やさない）。
- 割り付けセルは `M_20_40s` / `F_20_40s`（男女）に寄せる。手順13のセグメント別集計で
  `sex` 軸が意味を持つようにするため。
- 旧手順15の `ask`/`assume` 比較表と前提ブロックの説明は手順6へ、実行セルは新手順9へ移す。
- 旧手順15の `build_panel()` 再実行は削る（手順8で済んでいる）。変数名は `job` /
  `run_result` に一本化する。
- 付随して直すもの: 未使用だった `OPTIONS_5` を `q_intent` で使う、手順8の
  `importlib.reload()`（開発中の残骸）を削る、「手順N」の相互参照を新番号に直す。

### 3.3 `thinking` の未送信は別件として記録する

`model.thinking` は `validate` で False を強制され `run_metadata.json` に記録されるが、
Databricks へのリクエストには載っていない。issue の `thoughtSignature` がその証拠。
正しい抑止パラメータ名はエンドポイントとモデルで異なり、実機確認なしに実装すると
「無視されるパラメータを送って対処済みという記録だけが増える」ため、
`docs/issues/202607281100.md` に書き出して引き継ぐ。**今回は実装しない。**
